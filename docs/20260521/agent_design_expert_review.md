# XHS 智能运营智能体 — 架构审查报告

**审查日期：** 2026-05-21
**审查范围：** xhs-smart-operations-agent + xhs-feedback-loop 两个 change 的完整设计方案
**整体评分：** 6.5 / 10

---

## 1. 感知层（Perception）完整性

### 问题 1.1：感知视野仅限自身账号，缺失竞品/行业坐标系

**问题描述：** 当前感知信号来源只有两类：`trend_scanner` 扫描话题热门内容（公共信号），以及 `account_snapshots` 记录自身账号状态（私有信号）。但系统无法回答「我的收藏数下降，是因为我写差了，还是因为整个话题赛道流量在收缩？」——没有竞品账号或同赛道其他内容的基准数据，account_snapshots 的环比变化是噪音与信号混杂的，无法驱动有效决策。planner 的保守/激进配额调整（60%/120%）阈值，都建立在这个不可靠的基准上。

**严重程度：** 🟡 中

**建议：** 在 `trend_scanner` 的扫描结果中，额外提取同话题 TOP 10 笔记的收藏均值，作为「话题基准收藏数」写入 `topic_performance.topic_baseline_saves`。`agent_planner.py` 在做配额调整时，改为比较「我在该话题的 avg_saves vs 话题基准」，而非只看自身环比。这不需要引入任何新依赖，CDP 扫描时已经取到了那批数据。

---

### 问题 1.2：趋势扫描频率（每日一次，07:00）与热点时效性不匹配

**问题描述：** `agent_runner` 在 07:00 触发趋势扫描，但 XHS 热点（尤其是明星事件、突发新闻类话题）往往在午后或晚间爆发，当日产生的热点信号要等到次日 07:00 才能进入感知层。对于时效性内容，这意味着至少 12-24 小时的感知盲窗。trend-scanner spec 中没有任何应对突发热点的机制设计。

**严重程度：** 🟡 中

**建议：** 在 `daily-planner/spec.md` 中增加「热点窗口」机制：除每日 07:00 全量扫描外，在每日 14:00 增加一次轻量扫描（只扫 trending 关键词，不写 topic_performance，只产生临时热点信号），如发现新话题收藏速度 > 设定阈值，触发飞书推送让运营者决定是否插入当日计划。

---

### 问题 1.3：感知数据的可靠性验证机制缺失

**问题描述：** `account_snapshots` 依赖 `get_profile_snapshot()` 抓取粉丝数，设计文档已承认「粉丝数从哪里抓取」是 open question，降级逻辑是「存 null 不报错」。但 planner 会读取 `get_recent_performance(days=7)` 的环比变化来调整配额，如果连续多天粉丝数为 null，这个环比计算结果是什么？规划会静默错误地继续。trend_scanner 失败时同样只是「使用上次缓存的 topic_performance」——但 `topic_performance` 每周才更新一次，「缓存」可能是一周前的陈旧数据。

**严重程度：** 🔴 高

**建议：** 在 `memory-layer/spec.md` 中补充数据健康度检查：agent_runner 在规划阶段前，验证关键感知数据的时效性（`trend_updated_at` 距今是否 > 48h，`snapshot_date` 是否为今日），如超过时效则在飞书告警中注明「今日计划基于陈旧数据（X天前），建议人工确认」。针对 null 粉丝数，`get_recent_performance()` 需携带 `data_completeness` 字段。

---

## 2. 记忆层（Memory）设计

### 问题 2.1：topic_performance 每周更新一次，响应速度严重不足

**问题描述：** `topic_performance.avg_saves` 每周由 `reflection_runner` 更新一次（每周日 23:00）。但 planner 每天都在读这张表来决定「哪些话题是高表现话题」。这意味着：周三发现某话题开始爆发，要等到周日才能更新记忆，周一至周六的计划都基于上周的陈旧认知。极端情况下，一个已经凉掉的话题会在记忆层维持「高表现」状态长达 7 天。

**严重程度：** 🔴 高

**建议：** 将 `topic_performance` 的更新拆分为两层：(1) 每日增量更新，在 `agent_runner` 收到飞书回调、文章发布后，立即将该文章的 24h 数据写入 `topic_performance`（只更新该话题，加权计算近 7 日移动平均）；(2) 保留 `reflection_runner` 的每周全量重算作为数据修正。

---

### 问题 2.2：agent_strategy 表 + JSON 文件双写模式存在一致性风险

**问题描述：** 设计方案定义「JSON 文件为人工编辑的主源，SQLite 为运行时缓存」，但飞书回调写入 SQLite 时，JSON 文件写失败会产生分歧。运营者直接编辑 JSON 文件时，SQLite 缓存不会自动感知，会产生最长 1 分钟的静默错误窗口。

**严重程度：** 🟡 中

**建议：** 明确确定单一真相来源，推荐将 SQLite 作为真相来源，JSON 文件降级为初始化导入格式。直接编辑 JSON 的能力改为通过 Web UI 或 CLI 命令显式写入数据库。

---

### 问题 2.3：记忆数据缺乏时间窗口过滤，旧数据永久污染均值

**问题描述：** 一个话题如果 3 个月前表现很好，但最近 1 个月持续低表现，加权均值会被历史高峰长期拉高，导致 planner 持续将其归入「高表现话题」。`post_count` 越来越大，近期差表现的影响越来越被稀释。

**严重程度：** 🟡 中

**建议：** 在 `get_top_topics(n)` 实现中，增加时间窗口过滤参数：`get_top_topics(n, window_days=90)`，只基于最近 N 天内有发布记录的数据计算话题排名。超过 90 天无新发布的话题自动降级到「探索配额」。

---

## 3. 规划层（Planning）决策质量

### 问题 3.1：70/20/10 分配比例无动态调整机制

**问题描述：** 70%/20%/10% 比例被定为固定值，没有说明来源，没有机制允许随账号状态变化。每日配额只有 2 篇时，10% 保底 = 0.2 篇，整个分配框架退化成 1 高表现 + 1 探索的随机选择。

**严重程度：** 🟡 中

**建议：** 将比例改为可配置参数（`exploration_ratio`, `baseline_ratio`）存入 `agent_strategy.json`，并在周报中展示「本周探索话题命中率」。补充小配额下的整数分配规则。

---

### 问题 3.2：规划层对账号目标完全无感知

**问题描述：** 规划层所有决策都围绕「最大化收藏数」这一单一指标，没有任何「账号目标」的概念。会导致话题越来越集中（正反馈循环），长期降低内容多样性。

**严重程度：** 🟡 中

**建议：** 在 `agent_strategy.json` 增加 `current_goal` 字段（枚举：`growth/engagement/stability`），planner 根据目标调整权重参数。

---

### 问题 3.3：发布时间推荐逻辑存在统计混淆

**问题描述：** 「按小时分组统计平均浏览量，推荐 top 2 时间段」会把话题质量差异错误地归因为时间效应。在每日配额仅 2 篇的情况下，样本量永远不足以分离这两个变量。

**严重程度：** 🟢 低

**建议：** 数据不足阶段（发布历史 < 50 篇），直接使用经验最优发布时间，不要基于不足的数据做伪精确推断。

---

## 4. 执行层（Execution）可靠性

### 问题 4.1：CDP 作为执行核心，单点故障没有降级路径

**问题描述：** 整个智能体的执行层都依赖 CDP 浏览器自动化。CDP 失败的处理是「飞书告警，今日流程中断」，没有任何自动恢复逻辑。Chrome 崩溃、XHS 登录状态失效、页面结构变更都会导致当日运营计划归零。

**严重程度：** 🔴 高

**建议：** 增加 CDP 连接重试机制（30 秒后重试，最多 3 次）。将执行层分离为「需要 CDP」和「不需要 CDP」两部分：CDP 失败时，系统应能完成「使用缓存数据规划 → LLM 生成内容 → 推送飞书」的降级流程，只跳过「扫描」和「发布」步骤。

---

### 问题 4.2：低分诊断的 4 分支逻辑存在覆盖盲区

**问题描述：** 
- 分支冲突：`quality_issues >= 1` 且 `not has_image` 同时成立时，REGENERATE 优先于 WAIT_GALLERY，但重生成不能解决没有图片的问题
- HUMAN_REVIEW 兜底过宽，随规模增大人工队列会成为堆积点
- `publish_threshold` 在不同分支中比较不同字段（title_score vs content_score），语义混乱

**严重程度：** 🟡 中

**建议：** 改为显式优先级链：DISCARD → WAIT_GALLERY → REGENERATE → HUMAN_REVIEW。将 `publish_threshold` 拆分为 `title_publish_threshold` 和 `content_publish_threshold` 两个独立配置。

---

### 问题 4.3：执行状态与飞书审批之间存在竞态条件

**问题描述：** 运营者可能在 11:50 审批了 12:00 发布的文章，但 publish cron 在 11:45 已运行过一次（没有待发布文章），下次运行可能是 12:45，导致发布延误。

**严重程度：** 🟡 中

**建议：** publish cron 频率需细化为每 10-15 分钟运行一次，或在飞书回调写入 `publish_xhs=1` 时直接触发一次 publish 脚本。

---

## 5. 反思层（Reflection）有效性

### 问题 5.1：每周一次反思频率在账号表现急剧变化时严重滞后

**问题描述：** 账号被降权（近 3 日数据环比下滑 > 40%）时只会在飞书告警，但反思层不会因此触发紧急分析。偶然热点导致的异常高表现会在周一至周六持续推动「加量」决策，直到周日才能重新评估。

**严重程度：** 🟡 中

**建议：** 增加「触发式反思」：当 `account_snapshots` 连续 3 天环比下滑 > 20%，立即触发一次轻量反思并在飞书告警中附上数据摘要。

---

### 问题 5.2：Pearson r 用于维度权重决策，统计假设未被验证

**问题描述：** 
- 最小样本量 20 篇在每日 2 篇配额下需要 10 周积累，这期间算法可能已变化
- 同时对 19 个维度做相关性检验，没有 Bonferroni 校正，假阳性率约 64%
- 每次 +0.5 或 -0.3 无上限约束，权重会单调增加

**严重程度：** 🔴 高

**建议：** (1) 样本量门槛提升到 40 篇；(2) 增加 Bonferroni 校正（p 阈值 = 0.05/19 ≈ 0.003）；(3) `dim_weights` 增加上限约束（建议 3.0）；(4) 报告中标注置信度（低/中/高）。

---

### 问题 5.3：「纠正沉淀为定义更新」循环过长，中间状态无法利用

**问题描述：** 人工纠正 → 4 周积累 → reflection 提炼 → 确认 → 发布新版本。这个循环最短 4 周，意味着系统性评分错误会在这 4 周内持续污染相关性分析。

**严重程度：** 🟢 低

**建议：** 增加「即时生效」快速路径：同一维度连续纠正 ≥ 2 次时，Web UI 主动弹出「是否立即更新 edge_case？」提示，允许直接发布新版本。

---

## 6. Human-in-Loop 设计

### 问题 6.1：飞书是唯一的通知和审批通道，形成自我封闭单点

**问题描述：** 飞书既是审批通道，又是告警通道。飞书挂了，你既无法审批，又无法得知飞书挂了。`FEISHU_WEBHOOK_URL` 为空时所有方法静默返回——这意味着整个发布流程会静默停止。

**严重程度：** 🔴 高

**建议：** 飞书发送失败时，将待审批文章写入 `agent_strategy` 表的 `pending_approvals` key，并在 Web UI 首页显示待审批徽章（红点提示）。Web UI 必须是功能等价的备用通道，不能只支持只读查看。

---

### 问题 6.2：运营者未审批时系统状态不透明

**问题描述：** 没有「超时未审批」的处理逻辑。不清楚是运营者主动跳过还是没看到审批卡片。发布时间临近时没有提醒。

**严重程度：** 🟡 中

**建议：** 增加「发布前 1 小时提醒」。记录每篇文章的 `approval_status`（pending/approved/skipped/timeout），区分「主动跳过」和「超时未审批」。

---

### 问题 6.3：「每次操作 < 30 秒」目标与信息密度冲突

**问题描述：** 飞书卡片没有文章正文预览，运营者只凭标题和分数做审批，这是形式审批而非实质审批。每篇文章 4 个操作按钮增加了决策负担。

**严重程度：** 🟢 低

**建议：** 卡片增加文章前 100 字预览。「两个发布时间按钮」简化为一个「发布（推荐时间）」+ 一个「修改时间」按钮。

---

## 7. 整体 Agentic 成熟度

### 问题 7.1：系统目标是 L2.5，关键 L3 特性有设计缺口

**问题描述：** 按 Agent 成熟度评估：L1（工具调用）已完备，L2（计划执行）基本实现，L3（自主学习）只达到 L2.5——权重变更必须人工确认，维度定义改变需要 4 周周期，planner 规则是硬编码的。

**严重程度：** 🟢 低

**建议：** 在 `proposal.md` 中明确标注当前版本的 Agent 成熟度目标为「L2.5：有反馈的计划执行」，列出升级到 L3 的前置条件。

---

### 问题 7.2：「失败学习」机制不完整

**问题描述：** `DISCARD` 记录存在，但对 `topic_performance` 没有任何影响——因为 DISCARD 的文章没有发布，不会产生 `xhs_saves` 数据。系统学不到「这个话题连生成都过不了」这件事。

**严重程度：** 🔴 高

**建议：** 在 `topic_performance` 表增加 `discard_count` 和 `last_discard_reason` 字段。DISCARD 分支中写入 `discard_count += 1`。`daily-planner` 中，当 `discard_count >= 3` 且无任何成功发布记录时，自动将该话题降级到「观察期」。

---

### 问题 7.3：SQLite 单节点是未来扩展的结构性瓶颈

**问题描述：** 单一 SQLite 文件在多账号运营、任务队列、分布式场景下会遇到硬墙。

**严重程度：** 🟢 低（当前规模合理）

**建议：** 在 `design.md` 的 Non-Goals 中明确「单账号单机运行」假设，所有数据访问通过 `sqlite_db.py` 接口，不在业务逻辑层直接写 SQL。

---

## 最需要优先解决的 3 个问题

1. **CDP 单点 + 飞书单点的叠加风险（4.1 + 6.1）**：两个单点同时失效时系统完全静默停止。优先实现 CDP 重试机制 + Web UI 等价审批入口。

2. **DISCARD 不写回 topic_performance（7.2）**：系统只从成功学习，从不从失败学习。在 `topic_performance` 增加 `discard_count` 字段，在 planner 中过滤 `discard_count >= 3` 的话题。代码量 < 50 行，高价值低成本。

3. **Pearson 相关性分析统计可靠性问题（5.2）**：每次权重建议都可能基于假阳性信号。增加 Bonferroni 校正 + 样本量提升至 40 + 权重上限约束，并在报告中标注置信度。
