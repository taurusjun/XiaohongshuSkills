## 二、三轮迭代后仍存在的业务问题

### 问题 B — 冷启动期每日摘要缺少数据预期上下文 🟡 中

**发现：** `reflection-runner/spec.md` 规定冷启动期不触发自动 quick 分析，改为运营者手动上报。但运营者可能不清楚「冷启动期 0 收藏、个位数浏览是正常的」，可能在该触发手动上报时没有意识到，或者在正常波动时频繁误触发。

**建议：** 在 agent_runner 冷启动期的飞书每日摘要中增加上下文说明：「当前处于冷启动期（{N} 粉丝），数据波动正常，评论/浏览 0 是算法探测阶段的常态，无需担心」，并附上「本账号至今发布 X 篇，累计收藏 Y」的简单统计。

---

### 问题 C — DISCARD 文章进入实验发布的 Web UI 入口缺失说明 🟡 中

**发现：** `reflection-runner/spec.md` 说明「实验权重不影响低分处理逻辑，DISCARD 的文章需运营者手动在 Web UI 标记「强制候选」」，但 DISCARD 的文章不会出现在飞书审批卡片上（已被过滤），运营者若想对低分文章做实验，需要先到 Web UI 找到该文章，这个路径在 spec 中没有明确的 Web UI 入口说明。

**建议：** 飞书每日摘要中增加「今日丢弃文章」折叠列表（标题 + 丢弃原因），每篇提供「在 Web UI 查看」链接，使运营者可以从这里找到想做实验的低分文章并在 Web UI 强制候选。

---

### 问题 E — 竞品账号 user_id 配置说明缺失 🟡 中

**发现：** `trend-scanner/spec.md` 中竞品扫描依赖 `competitor_accounts`（user_id 列表）配置不为空才生效。XHS user_id 不像用户名那样容易获取，如果这个字段在上线后一直为空，P1 功能等于永远不会启动。

**建议：** 在 `agent_strategy.json` 中提供示例格式和说明（「如何获取 XHS user_id：在 PC 端打开竞品账号主页，URL 中 user_profile/ 后面的字符串即为 user_id」），并在飞书 P1 功能启动提醒中包含这个配置说明。

---

### 问题 F — agent_strategy JSON 修改后静默失效 🟡 中

**发现：** `memory-layer/spec.md` 规定「JSON 仅作初始化导入格式，运行时不直接读取 JSON 文件，表为空时读 JSON 做一次性导入」。如果运营者在数据库已初始化后修改了 JSON 文件，修改不会生效，系统不会有任何提示。这是一个典型的「静默失效」场景。

**建议：** 在 `agent_runner` 启动时比较 `agent_strategy.json` 的 `last_modified` 时间戳与数据库最后初始化时间，如果 JSON 比数据库更新，飞书推送告警「⚠️ agent_strategy.json 已修改，但系统使用数据库值。如需应用新配置，请在 Web UI 重新导入或使用 CLI reload-strategy」。

---

### 问题 G — 封面图 base64 大小未做预检 🟡 中

**发现：** `cover-image-scoring/spec.md` 规定图片以 base64 传给 DeepSeek，但没有定义传入前的大小预检逻辑。高分辨率写真图（4-8 MB）base64 后体积显著增大，既会拖慢 API 响应，也可能触发 DeepSeek 的请求大小限制。降级 Scenario 是被动处理，浪费了一次 API 调用。

**建议：** base64 传入前增加一步：图片尺寸超过 1280px 长边时先用 Pillow 做 resize，确保传入 DeepSeek 的图片 base64 编码后 < 1MB。

---

### 新问题 1 — 14:00 追发热点的目标发布时间不明确 🟡 中

**发现：** `trend-scanner/spec.md` 规定 14:00 补扫发现热点后，运营者确认追发，触发临时抓取+生成流程。从确认到生成完成估计需要 20-40 分钟，完成后推荐「当前时间 + 30 分钟」发布（约 15:00），但 15:00 不在 `default_post_times` 列表中。如果等到 18:00，热点内容从 14:00 确认到发布已滞后 4 小时，时效性严重损失。

**建议：** 明确 14:00 追发热点内容的发布时间策略：追发内容目标发布时间 = 生成完成时间 + 30 分钟（审批窗口），不受 `default_post_times` 约束，单独创建临时发布任务，飞书追发确认卡片中明确告知「预计发布时间：约 HH:MM」。

---

### 新问题 2 — 观察期话题遇新热点无提醒机制 🟡 中

**发现：** `daily-planner/spec.md` 规定话题 `discard_count >= 3 且 post_count = 0` 进入观察期，必须运营者手动在 Web UI 恢复。但进入观察期的话题可能只是因为那段时间素材不足（Yahoo Japan 报道密度有周期性），而非话题本身没有价值。一旦进入观察期，即使 trend_scanner 检测到 `is_fresh=True` 的新热点，planner 也不会为其分配配额。

**建议：** 增加半自动恢复机制：当观察期话题的 `is_fresh=True` 时，飞书推送「📢 观察期话题 [{话题名}] 出现新热点信号，建议评估是否恢复测试」，附「一键恢复到探索配额」按钮。不自动恢复（保持运营者控制权），但主动提醒。

---

### 问题 D（低优先级）— 多篇发布到 T+2h 时通知可能过密 🟢 低

**发现：** 账号积累到成长期（每天 2-3 篇），每天会收到 2-3 条 T+2h 提醒，加上每日摘要、热点追发通知、超时未审批提醒，可能产生通知疲劳。

**建议（可后期迭代）：** `agent_strategy.json` 增加 `notification_consolidate` 配置，当天多篇到 T+2h 时合并为一条推送。
