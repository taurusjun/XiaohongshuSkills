# LLM 前缀缓存 & prompt 布局约定

> 结论来源：2026-10-16 实测（DeepSeek `deepseek-flash`，`prompt_cache_hit_tokens`）。

## 一句话规则
**固定块（角色 + 规则 + 输出格式）必须排在 prompt 最前面；变化内容（标题/正文/素材）放最后。**
前缀缓存只认「从头开始、连续相同的前缀」——固定块只要排在变化内容之后，就**永远不命中**。

## 实测机制（重要）
| 固定前缀大小 | 第1次 | 第2次 | 说明 |
|---|--:|--:|---|
| ~117 tok | 0 | **0** | **太短 → 缓存根本不启用** |
| ~273 tok | 0 | 128 | 启用，命中 1 块 |
| ~657 tok | 256 | 512 | 多块 |

- **最小前缀门槛**：前缀 ≲200 token 时**完全不缓存**。
- **缓存粒度 = 128 token/块**：命中量恒为 128 的整数倍
  （实测 `title_pass2` 1152=9×128、`generate` 1536=12×128、`story` 896=7×128、`score` 2560=20×128）。

## fetch 各 stage：改造前后（10-16 基线）
| stage | 固定块位置 | 命中率 改前 → 改后 | 每日可省 |
|---|---|--:|--:|
| `score`（评分，21 维定义） | 已在前 ✅ | 77% → 77% | — |
| `title_pass2`（Pass2 标题） | 后 → 前 | **0% → 61%**（1152 tok/次） | ~25k |
| `generate`（资讯体生成） | 后 → 前 | **22% → 65%**（1536 tok/次） | ~51k |
| `story`（故事体生成） | 散在中间 → 前 | **3.8% → 40%**（896 tok/次） | ~20k |
| `caption`（短配文） | 后（且固定块仅 ~130 tok） | 0% → 仍 ~0% | ~7k（上限低，**未改**）|

合计：约 **96k token/天** 的输入从「未命中」变为「命中」（命中约按 1/10 计价）。

## 代码里的约定
1. **固定块在前**，末尾用统一分隔符接素材：
   ```
   [固定] 你是…（角色）。规则：…。严格只输出 JSON。格式：{"..."}
   ===== 素材 =====
   [变化] 原标题：… 正文：… 导语：…
   ```
2. 改 prompt 时**只调顺序、不改内容**，并实测三件事：
   - `usage().cache_hit_tokens` 上升；
   - 输出 JSON **解析正常**、字段齐全；
   - 抽查生成质量（标题/正文）无变化。
3. **别把变化内容嵌在固定块中间**——`story` 原来在固定块中间夹了 4 处变化
   （`angle_note` / `参考原标题` / `img_note` / 原文），导致前缀第 2 行就断、命中 3.8%。

## 怎么自查某个 stage 为什么没命中
1. 看布局：固定块是否从**第 1 行开始连续**？变化内容是否都在其后？
2. 看大小：固定前缀是否 ≳200 token（否则缓存不启用）。
3. 实测：同一 prompt 连调 2–3 次，看第 2/3 次的 `cache_hit_tokens`
   （第 1 次必然 miss，冷启）。
