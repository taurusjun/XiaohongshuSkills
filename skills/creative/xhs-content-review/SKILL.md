# 小红书内容审查

## 执行顺序（硬约束）

加载此skill时，**必须先执行以下前置步骤，再进入评分**：

### 步骤1：内容密度否决项检查

在评分之前，先检查每篇稿件的**内容密度**。

**字数计算必须调用脚本，禁止自己实现。正文和标题用不同算法：**
```bash
SCRIPT=~/.hermes/skills/creative/xhs-write-publish-flow/scripts/xhs_word_count.py

# 正文字数（所有字符×1，换行不计）
python3 $SCRIPT "正文内容"                    # → 920字
python3 $SCRIPT --check "正文内容" 1000       # → ✅  920字/1000上限

# 标题长度（CJK×1，其余×0.5，含英文/数字/假名）
python3 $SCRIPT --check-title "标题文字" 20   # → ✅  标题19字/20上限
```

1. 从DB读主素材content_ja + 每个related_keys素材的content_ja
2. 按 `。！？` 拆分为句子，用 set() 去重后拼回
3. 用脚本计算 `xhs_word_count.py "正文"` 得到字数，再除以 `len(去重后原文) * 100` 得到密度
4. 低于 **30%** → 判定"信息增量不足"，退回补充素材或合并关联条目，**不进入评分**

**⚠️ 先按 `channel` 分流（9/28–10/1 四日批新增）：** 密度门只卡 xhs 稿。`channel='gzh'` 的稿件（写了 `wechat_title/wechat_content`）走公众号评审（去魅测试→背景锚定→三维度评分，及格线 7 分），**不要用 xhs 的 30% 密度门去卡它** —— 本批 `16be29323473`（道枝骏佑深访，ja 4951 / 正文 867）按 xhs 口径只有 17.5% 会被误判退回，按 gzh 口径正常并已落盘 8.4 分。批量密度全检时先分组（xhs / gzh），再各自套门。

**⚠️ 豁免必须在 score_dims 理由里写明口径：** 多艺人活动报道（目标人物是 8 位班底之一，如本批 `1b0427b9c58d` 的 7000 人词典活动）与目录型素材（作品一览占原文过半，如 `345622d0b5f0` 的 Prime 片单）走密度豁免；榜单/公告/商品发布类走「天然上限」。**这两类都要在落盘的 score_dims 理由里写明豁免或上限口径**，否则次日复盘分不清是漏检还是豁免。

#### 密度计算例外：综合时间表/多艺人报道（7/2经验）——仅供参考，启用需用户明确授权

当 content_ja 是**多艺人综合报道/时间表/活动日程**（如FNS歌谣祭全时间表、音乐节出演名单、颁奖礼全程报道）时，目标人物只占原文的一小部分。此时密度计算可能失真。

**但注意：** 用户明确要求过「豁免需要我同意」。不要自行判定豁免。如实报告密度后由用户决定是否走豁免路径。

- **不当做法**：用整篇 content_ja 的字数做分母 → 密度看起来极低（如能年玲奈FNS压轴：652xhs字/2500ja字=26.1%），但其实改写用了足够的历史上下文（DB中该人物11条历史记录）
- **正确做法**：判断原文类型。如果是综合时间表/多艺人列表：
  1. 尝试提取目标人物相关的原文片段作为分母（需要区分原文中目标人物的部分 vs 其他艺人的部分）
  2. 如果无法精确拆分（如时间表正文未单独分段），则**豁免密度检查**，改为手动判断「信息增量」：检查改写是否用了DB中的历史记录来充实内容
  3. 能年玲奈案（7/2）：content_ja 是2500字FNS完整时间表，能年仅出现1行。但改写结合了DB中11条历史记录（6/14重返富士→6/17片场→7/2FNS压轴），信息增量充足，豁免密度检查
- **判定标准**：如果原文是「报道A的报道，A只是众多条目之一」，则走豁免路径；如果原文就是专门讲A的但字数少（如短讯形式的AKB行程），则正常计算密度

#### 密度计算例外：综合采访报道/多人同期受访（7/6经验）

当 content_ja 是**多人同时受访的采访报道**（如新闻发布会、集体采访、节目录制后群访），其中目标人物只占原文1/3以下内容时：

- **典型场景**：一家电视台/网站发布了一篇多名嘉宾共同出席的记者会全文，目标人物（如峯岸南）只是4位受访者之一，其个人发言仅占全文20-30%
- **判定标准**：
  - 如果原文标题/导语明确是「A和B等出席XX活动记者会」形式的综合报道 → 走豁免路径
  - 如果原文标题/导语是专门讲目标人物的个人采访 → 正常计算密度
- **操作流程**：
  1. 判断原文是否为多嘉宾综合采访
  2. 如果是，豁免密度检查，改为手动判断信息增量
  3. 手动判断：能否从采访中提取出至少1-2个有画面感的直接引语/事件？引语是否包含可验证的细节（时间、地点、具体台词）？
  4. 正文通常300-500字即可，不需为拉密度而注水
  5. 写稿后标注「综合采访报道豁免密度」
  6. 如果有多个DB key对应同一事件的多个来源报道（不同媒体写同一场记者会），选content_ja最长的做为主素材key，其他通过related_keys关联
- 详细案例：`references/7-6-density-exemption-multi-guest-interview.md`

#### 行业分析/评论型素材的密度陷阱（7/21经验）

当原文是行业分析/评论型长文（而非新闻事件/人物报道），正文写得精简但覆盖了原文所有核心论点时，密度可能远低于30%。这类原文的特点是：
- 观点+案例相互缠绕，原文有大量重复论述
- 核心论点通常只有4-6个，剩下的都是换角度重述
- 不能用深访类的「补充引语和细节」来拉密度

**正确的扩充路径**不是硬加观点，而是从原文中段挖掘可用的案例和数据（如海外对比案例、行业数据、艺人具体发言），整理为新段落补充进去。

**判定标准：** 先判断原文类型（新闻事件 vs 行业分析 vs 人物深访），再用对应的扩充策略。具体策略参考 `xhs-write-publish-flow/references/analysis-opinion-density-expansion.md`。

当 content_ja 是**品牌合作/杂志产品推荐/开箱文**（如板野友美在《MAQUIA》推荐防晒衣，全文80%是产品描述、材质介绍、购买信息）时：

- **判定标准**：全文的核心叙事内容（人物自述、经历、观点）是否只占原文很小比例（≤30%）？
  - 如果是 → 豁免密度检查，但需判断是否值得写：
    - 如果其中有可独立提取的人物引语/生活片段（如「骑车接送娃→防晒心得」），可以写一个简短的日常笔记
    - 如果纯粹是产品功能罗列+tittle（穿搭物品表），跳过
  - 如果原文人物叙事占主导（像访谈类而非开箱类）→ 正常计算密度
- **7/6案例**：板野友美防晒衣稿（2766字content_ja → 只有322字可用内容，密度12.6%）。原文是杂志美容连载商品推荐，板野的个人防晒心得只占开头几段，后面全是dazzlin连衣裙、emmi衬衫等产品参数和价格。判定：品牌合作软文，个人故事薄，跳过。
- **判定流程**：遇到疑似品牌合作/产品推荐的素材时，先读到content_ja的前30%，判断内容性质（人物叙事 vs 产品介绍）。如果后70%全是产品参数/购买链接/穿搭列表，直接判定为品牌合作软文，整篇跳过。

#### ⚠️ Pitfall：正文跨小节重复——密度达标但内容重复（8/17案例）

密度检查通过 ≠ 内容无重复。8/17 村山美羽稿（852字/42.0%，机械检查全过）通读时发现「酱油学校」场景在「汤船泡10小时」和「埼玉的俘虏」两个##小节各写了一遍，几乎逐字重复——重复段落虚增正文字数，密度检查反而显高。**评分前的通读必须顺带检查跨小节重复：同一场景/引语/细节是否在不同小节出现两次。** 修复：删冗余段→用素材中未使用的细节补字数（该稿用「所泽行程+埼玉段子」替换重复段，字数不降反升）→重跑假名+renwei→重入库→重评分。批量review时尤其要警惕：批量写稿模式下同一段素材细节容易被复制到多个小节。

**8/31批量22篇再犯（2篇，都靠评分前通读全文揪出）：** ①AKB1仁藤萌乃「雷阵雨→晴天+晴女保证」段在正文出现两次（扩充patch新增段落与原段几乎逐字重复）；②A4木元由子「森尾由美鼓励+桑田靖子发排练视频」细节跨两个##小节各写一遍。两篇密度都达标（68.3%/65.0%），纯靠通读发现。**根因：扩充时把「已写过的信息点」当成新内容再加一段（8/13/8/18同一机制的第三次发作）。** 对策升级：①扩充前先列「已写信息点清单」（关键引语/配角细节/数据），新增内容必须不在清单里；②评分前通读时重点扫「配角姓名」（森尾由美、桑田靖子这类）——同一个配角名字+同一句引语出现两次=重复；③删冗余段后字数可能跌破800（A4删后不足），用素材中未使用的粉丝评论段补足，再重跑假名+renwei+重入库。

**9/3机械查重法（重复段检测脚本，伊藤百花9857字稿案例）** — 伊藤百花深访稿因python `c.replace(anchor, add)` 追加时add与已存在段落重复（「她讲了个动人的背景…」段出现两次），重读全文时才抓到。**批量review的机械预检可以自动化找重复句：** 按句号/感叹号拆句，筛>20字句子，用 set 找重复——命中的就是疑似重复段（同句出现2次）。```python
import re
c = open(fn).read()
sents = [s.strip() for s in re.split(r'[。！？]', c) if len(s.strip()) > 20]
seen = set()
for s in sents:
    if s in seen: print('重复句:', s[:50])
    seen.add(s)
```
命中后确认是否同一信息点写两遍，删冗余段后**必须重算字数/密度**——9/3实测伊藤百花删重复段后3059→2923字跌破30%密度线（需2957），追加新段落补回3038字才过线。删段后的密度回落是必查项，不是可选。

### 步骤2：基调匹配检查（新增——在renwei审读之前做）

写完后先判断这篇素材属于哪种读者预期：

| 读者想看什么 | 写作基调 | 反面案例（本session） |
|-------------|---------|---------------------|
| **看戏型**（综艺趣闻/偶像日常） | 轻松、带笑、别在段尾总结金句 | 柏木由纪初版：每段结尾写排比金句→被用户批评"太严肃" |
| **共情型**（逆袭/成长/离别） | 克制、留白、别煽 | — |
| **吃瓜型**（八卦/争议/内幕） | 直接扔料、别铺垫 | — |
| **学习型**（行业分析/人物深度） | 冷静、信息密度高 | — |

判断方法：问自己"一个普通路人点进来想看什么"，不是"我想表达什么"。
如果基调偏了，只改开头3行和结尾段——改调不改骨架。

### 步骤3：renwei审读（去AI味）

- 调用 `skill_view(name='renwei-writing')` 加载审读标准
- 用**审读模式**（全文扫信号，不是打磨模式只扫动过的句子）
- 按post-edit-checklist六类信号逐条过全文：意义拔高、宣传腔、句式套路、格式痕迹、语气痕迹、填充与对冲
- **日文假名预检（新增7/14）**：在renwei审读之前，先做日文假名计数检查。如果正文中含>5个假名，先退回到写稿阶段替换所有日文引语为中文，再回来审读。假名计数命令：`python3 -c "c=open('draft').read(); print(sum(1 for ch in c if '\u3040'<=ch<='\u309f' or '\u30a0'<=ch<='\u30ff'))"` — 输出必须≤5。
- 优先用自动化脚本：`python3 ~/.hermes/skills/writing/renwei-writing/scripts/renwei-pre-commit.py`
  - 退出码 0 → 通过，进入评分
  - 退出码 1 → 拒绝，必须改稿
  - 退出码 2 → 警告，检查非聚集信号后决定
- 每处改动只做减法（删/替换），不重写
- 改完后重新入库，再进入评分

#### 引语内格言匹配的false positive（7/1经验）

当renwei拒绝原因是「格言公式(X是Y的Z)」且命中内容是**对被采访者/引用者原话的转述**时，需做引语判断：

1. 逐处检查命中位置是否在 `" "`、`「」`或紧跟在「某人说/认为/的意思是」之后
2. 如果内容是**对原文观点的事实转述**而非自己写的拔高总结（如「铃木收认为，个人和机构都要尽快用自己的语言发出去」是在转述铃木收的观点，不是自己加的格言）：
   - 优先换主语（「他认为…」→「按他的说法，…」）
   - 拆成两句（「铃木收提出一个观察。个人和机构都要尽快用自己的语言发出去」→去掉冒号/逗号分隔）
   - 如果以上都不行，直接把该句并入前一段或后一段，破坏"独立格言句"的句式结构
3. 避免为了过renwei而歪曲被采访者原话

#### Renwei失败修复模式（来自6/21 session实案）

**最常见的聚集信号：短句轰炸 + 破折号集群**

当renwei拒绝（exit 1）且命中集中在「短句轰炸」和「破折号」两类时，采用以下修复步骤：

1. **短句轰炸修复**：将连续3个以上独行短句（「好难！」「看不懂…」「太真实了吧！」）合并为叙述性的一句话。如「现场炸了。平日里在舞台上唱唱跳跳的两组偶像，面对逆再生舞蹈也毫无招架之力。」替代「好难！\n看起来好难…\n这什么啊…」——保留核心信息，去掉重复情绪表达。

2. **破折号集群修复**：破折号超过3处时，逐处替换为：
   - 冒号（解释关系）：「主题是——」→「主题是：」
   - 逗号+「而」（转折关系）：「A——B」→「A，而B」
   - 逗号（并列关系）：「总监——编舞师」→「总监、编舞师」
   - 句号（截断长句）：「当……时——当……」→「当……，……。会是谁……？」

3. **升华结尾修复**：结尾「因为她们知道——只有在最艰难的挑战面前仍然保持笑容的人，才能被称为真正的偶像」类句子——直接删掉最后1段升华。/改为自然收束（「会是谁的舞步更接近完美呢？」留下悬念即可）。

4. **改后重跑验证**：patch完draft文件后立即重跑renwei脚本，确认exit 0再入库。如果还有残留，继续做减法直到通过。改稿只做减法——不重写句子，只删/换。

### 步骤3.5：review强制执行铁律（7/1追加）

**入库后必须立即执行review，这是不可跳过的闭环步骤。**

| 违规场景 | 根因 | 规则 |
|---------|------|------|
| 改稿后跳过review直接入库 | 认为"renwei已过=质量合格" | renwei确认无AI味 ≠ 稿件质量达标。5维度review是独立于renwei的强制步骤 |
| 覆盖重写（改小标题/删内容/重写）后跳过review | 认为"内容改动小，不需要重跑" | 即使只是调整段落结构、加/改小标题、删减内容，也必须重新走review |
| 写稿过程中跳顺序（入库→汇报→补review） | 想先让用户看到进度 | 入库一篇review一篇，全部完成后才汇报。向用户汇报本身如果在review之前=违规 |
| 用户说"改到900字"后改完直接入库 | 认为字数符合要求就行 | 改稿→入库→review→汇报，缺一环都不算完成。入库和review之间不能插入任何动作（包括向用户汇报进展）|

**自检口诀：** renwei过了 → 入库了 → 必须review。入库后不做review就汇报=流程断裂。

**⚠️ 批量review纪律（6/21教训——先全部查密度再逐篇评分）：**

一次review多篇稿件时，必须先做密度全检再做评分：
1. 查出所有写过正文的稿件的rewritten_content、content_ja、channel
2. 统一计算每篇的密度
3. 输出密度总览表（哪些退回、哪些例外候选、哪些通过）
4. **告知用户退回清单后再进入评分** — 密度不达标的稿件不进评分流程
5. 对剩余稿件按优先级（长文story优先于短news）逐篇评分

**严禁先评一篇就输出报告让用户决策，然后又补第二篇。** 所有结果在同一个报告中输出。

按 `xhs-write-publish-flow/references/chinese-review-criteria.md` 的5维度标准评测：

| 维度 | 分值 | 说明 |
|------|------|------|
| 爆发点 | 2分 | 开头是否有钩子、冲突、悬念 |
| 情绪价值 | 2分 | 读者有无情绪波动、记忆点 |
| 信息增量 | 2分 | 对比原文的新角度、深度 |
| 内容深度 | 2分 | 背景交代、人物关系、路人性 |
| 标题质量 | 2分 | 钩子、数字、矛盾，xhs_len不超字数 |

满分10分。

**通过标准（按稿件类型区分）：**

| 稿件类型 | 判定 | 说明 |
|---------|------|------|
| **长文story**（DB `format='story'` 且 `is_long_form=1`） | **需≥8分**才通过，且必须有##小标题分段 | 长文投入大，质量必须到位 |
| **短news**（非story素材：`format='news'` 或 `is_long_form=0`） | **不强求8分**，内容密度+格式检查通过即可 | 轻量跑量，不过度精修 |
| **AKB大TOP纯入库**（summary子弹，无正文） | **不评分**，只设preselected=1 | 纯粉丝向短讯/晒照/行程，不走review |
| **AKB大TOP写了正文的短news** | 按短news标准 | 入库优先，内容密度+格式通过即可 |
| **公众号稿（gzh channel）** | **走公众号评审**，不按xhs 5维度评分 | 去魅测试→背景锚定→三维度评分，合格线7分 |

**体裁判定方法：** 入库后从DB查 `format` + `is_long_form` 字段确认。不用正文字数反推体裁。详见 `xhs-write-publish-flow` 的「体裁判断（根据DB字段）」。

**翻译版（DB content字段）review规则（7/1追加）：** 用户要求"跑review看content"时，指的是素材原文的中文翻译版本（DB的`content`字段），不是改写版。翻译版和改写版评分标准不同：

| 差异点 | 翻译版（content） | 改写版（rewritten_content） |
|--------|-----------------|---------------------------|
| 信息增量 | **不计分**（纯翻译无新增） | 正常2分 |
| 标题 | **不计分**（无改写标题） | 正常2分 |
| 满分 | **6分**（只评爆发点+情绪+深度，各2分） | 10分 |
| 判定标准 | 作为**资料参考**，不是可发布稿 | 作为可发布稿评分 |
| 典型分数 | 5-6分为合格翻译 | 8分以上为达标改稿 |

注意：用户说"跑文章review"时，可能指的是素材原文的翻译版content，而不是你的改写版。先确认用户要看哪个版本再评分。

**长文结构要求：** 正文超过6段逻辑段落（多个主题切换）时，必须有##小标题分段。连续6段以上无标题的散文式排版被用户批评为"一团糟"。人物深度长文至少每2-3段一个##标题，帮助读者快速定位叙事线。

**吃瓜型/争议型写作规范（7/6追加）：**

| 维度 | 要求 |
|------|------|
| 写作立场 | 不站队、不评价。只摆事实和各方观点，让读者自己判断 |
| 结构 | 不要先定调再论证。按「原发言→各方反应→圈外人参与→时间线拉远看同类争论」铺开 |
| 文化梗本地化 | 日本特有的笑点/梗（如"和田アキ子→磕头"是演艺圈地位梗），必须替换为中文读者能秒懂的表达：「磕头」→「我哪敢，直接跪」；「演艺圈大姐大」替代「和田アキ子」作为前置定语 |
| 冲突价值判断 | 不要自动跳过"看起来有争议的素材"。争议型素材天然有互动潜力，关键在写法（中立、多层视角）而非素材本身"值不值得写" |
| 小标题 | ##小标题用具体事件/引语句，不要用抽象概括。如「搞笑艺人蹭热点：列了一份谁付谁不付清单」而非「另一方的声音」 |
| **标题设计（争议/吃瓜型）** | 标题必须自带**对立冲突**，不要做中立概括。格式：「她说X，评论区追着她骂了三天」vs「一句话炸出三代人」（后者太平）。具体公式：主语A的立场 + 反方反应（追着骂/吵翻了/炸了）。标题最前面放具体引语/动作，不要用"关于X这件事/说到X"开头 |
| **AI味高发区清单（7/6补充）** | 以下句型/写法每次写完必须自检替换：<br>①「没有标准答案，但至少说明……」→ 直接去掉或用反问「所以你……？」收尾<br>②「A是X，B是Y，C是Z」三连标签式总结 → 改为口语化并列「有人X，有人Y，有人Z，还有人干脆……看人」<br>③「远没有定论」→ 直接删，用具体动作/场景收束<br>④ 原文引语中的破折号 → 确认是被采访者原话（保留）还是自己加的叙述（替换为逗号/冒号）|

**改稿决策逻辑：**
- 长文story（DB `format='story'` 且 `is_long_form=1`）未达8分 → 只修最低维度 → **重跑renwei（exit 1则继续改）** → 重入库 → **重读全文后重新逐维度评分**（禁止预估评分——不能根据改了哪些点就做分数调整，必须实际重读正文再打分）
- ⚠️ **为过 renwei 的改稿会把正文压到 800 以下——改完必须重跑字数门（不能只重跑 renwei）。** 10/7 实测 f733b80ebcea 初稿 815 字过 precheck，因 renwei exit1（两处「意义拔高」聚集）删改结尾段后掉到 799（<800 硬门），靠重跑 `batch_precheck.py` 才揪出，再补一句素材内陈述句到 834 才放行。**闭环 = renwei → 字数重计 → 重跑 batch_precheck（假名/新字体已含其中）→ 重入库。** renwei 报告里的 `(xhs: N)` 是另一套口径，本批实测比脚本低约 40 字，一律以脚本为准。
- 短news/纯入库 → 不进改稿循环

#### ⚠️ Pitfall：入库后跳过review直接汇报（7/28重犯）
review是入库后不可跳过的闭环步骤。入库一篇→立即review一篇→全部完成才汇报。
**在review完成前，不要向用户输出任何「已完成」类表述。** 用户发现review缺失时的反应是直接质问——不是温和提醒。
自检：入库动作完成→停顿→问自己「我跑review了吗？」→没跑就立即跑，不允许先汇报再补review。

#### ⚠️ Pitfall：改稿循环第1轮结束后停下来询问用户（7/28重犯）
if-then规则：「未达8分→立即开始第N+1轮改稿，不输出任何询问性文字，不等待用户下一步指令，不停顿」。
第1轮改稿出分后发现有未达标稿件时，**必须自动继续第2轮**。禁止输出类似「继续第2轮改稿还是到此为止？」的询问——这违反了if-then规则，用户需要解释「循环是什么意思」才让我继续。
正确行为：改稿→renwei→重入库→重review→检查是否全部≥8分→否→自动继续→最多3轮→第3轮后如实告知剩余差距。

#### 已知的review天花板：节目公告/出演信息类素材——7.5~7.9分封顶（7/28确认，8/11表纸公告验证）

**8/11验证：** 表纸/杂志封面公告类（B.L.T.封面特辑宣传文、无艺人引语、无悬念冲突）同样封顶——小坂菜绪B.L.T.封面稿7.8分（爆点1.5/情1.5/增1.5/深1.5/标1.8），标注「表纸公告类天然上限」通过，不进改稿循环。判定标准同公告类：原文是封面预告/拍摄花絮宣传而非人物故事时，先试「把最有趣的拍摄细节提到第一行」一招，仍7.5~7.9则按天然上限通过。

当素材原文是**TV节目出演名单/音乐节目曲目公告/活动日程通知**（如CDTV lineup、节目出演者一览、活动时间表）时，原文不含任何人物引语或细节描写，改写稿在5维度review中天然具有上限：

| 维度 | 为何上限低 | 典型分 |
|------|-----------|-------|
| 爆发点 | 公告类开头难有悬念/冲突 | 1.5~1.8/2 |
| 情绪价值 | 无人物引语可挖，读者获取信息而非情感共鸣 | 1.0~1.3/2 |
| 信息增量 | 核心信息就是公告本身，扩展空间有限 | 1.5/2 |
| 内容深度 | 可加背景分析但无法弥补引语缺失 | 1.5/2 |
| 标题质量 | 可做得好但缺少冲突点 | 1.5~1.8/2 |

**7/28验证：** 伊藤百花CDTV出演稿经3轮改稿（改开场为聚光灯画面、换标题加数字和"接力棒"比喻），从6.6→7.9止步。第3轮仍差0.1分。根因是原文是CDTV节目出演名单公告（SUPER EIGHT/优里/ME:I等的曲目安排），没有伊藤百花本人的引语或人物故事可挖。

**判定流程：**
1. 首次review如总分<8分且素材类型为节目公告/出演名单/日程通知 → 改1轮
2. 改后如仍在7.5~7.9区间 → 标注「节目公告类天然上限」通过
3. 如总分<7.5 → 需判断是否是公告类上限还是写作质量问题
4. **注意：** 如果节目公告素材中包含大量艺人引语/幕后故事（如出演者采访视频的文字稿），按正常长文story标准评分≥8分

**⚠️ 天花板可突破（8/4验证）：** 公告类素材虽无人物引语，但改稿方向正确可破7.9——坂道募金（纯官方募捐公告，无任何引语）首轮7.8，通过①开头加事件背景数据锚点（「熊本地震过去一周，遇难38人，超8000人避难」）②标题加读者参与感钩子（「你投下的每一份心意，都全额捐给红十字会」），第二轮8.4通过。**先试这两招再判天花板**，不要首轮未达8就直接套「天然上限」跳过改稿。

**⚠️ 9/16追加：把「最戏剧性的细节搬到第一行」是表纸/商品公告/番组预告这三类的破线手法，写稿阶段一次到位、不产生改稿轮。** 三例实测：①杂志公告（MAQUIA 22周年・三封面）→ 用受访者原话当首句（「自己是独一无二的存在，不属于任何人」），爆发点1.6→1.8、总分8.2；②商品公告（小栗有以2027日历）→ 用画面开场（「清晨的客厅，晃到街上的下午，还有隧道和人行天桥之间那点光」），总分8.0；③TV特番预告（秋刀鱼×好吃便宜合体SP）→ 把主持人原话提为第一句（「如果是放VTR，主持起来还轻松，可素人直接进到演播室里，局面就完全不一样了」），总分8.1。共同点：引语/画面本来就在素材中段，只是被公告式的日期开头压住了——搬到第一行即可，不动骨架。改完必须重跑 renwei（提行后可能触发新命中）+ 重入库（重带 related_keys）。

**⚠️ 9/3新增：晒照型 story（lf=1）的7.9分天然上限（小栗有以海边照案例）** — 纯照片/写真描述类素材即使 DB 标记 `format=story, is_long_form=1`（被要求按长文写800+字），在5维度review里仍有天然上限：原文只有画面白描（服装/姿势/背景），无事件冲突、无直接引语、无人物心路，爆发点1.6/情绪1.6/增量1.4/深度1.5/标题1.8=7.9分。**判定流程：** ①首次review <8分且确认素材是纯晒照描述 → 不硬凑改稿循环（没有引语/细节可挖，改开场提画面细节已尽力）②标注「晒照类天然上限」通过③区别于「轻量story卡爆发点7.5」——晒照类没有可提取的画面钩子以外的增量材料，轻量story通常还有制度反差/引语可用。**注意：** 若晒照素材含人物自述/评论反应/心路（如评论区争议、当事人谈身材管理），仍按正常story标准评分。小栗有以案例同时踩了「人名嶋字误伤」（替换表把小嶋阳菜写成小岛阳菜，人名嶋保留——见 xhs-write-publish-flow 假名自检节）。

#### 已知的review天花板：美妆/产品导向类素材——7.5~7.8分封顶

美妆产品推荐、杂志商品合作类素材（如樱坂46守屋丽奈《MAQUIA》蓝调粉色妆容稿）在5维度review中天然具有上限，原因：

| 维度 | 为何上限低 | 典型分 |
|------|-----------|-------|
| 爆发点 | 产品介绍型开头天生温和，无法做到"悬念/冲突"式开场 | 1.5~1.8/2 |
| 情绪价值 | 偏实用型内容，读者获取信息而非追求情感共鸣 | 1.5/2 |
| 信息增量 | 产品心得翻译转写，原创穿角空间有限 | 1.5/2 |
| 内容深度 | 美妆理念传达可做到位但无法展开人物故事 | 1.5/2 |
| 标题质量 | 金句感可做得不错但钩子不够尖锐 | 1.5/2 |

**7/27验证：** 守屋丽奈稿经3轮改稿（改开场、加个人化妆背景、强化学科性结尾），从7.5→7.8止步。第3轮结果确认：美妆产品类素材的review天花板约7.8分。

**判定流程：**
1. 首次review如果总分<8分且素材类型为美妆/产品推荐/品牌合作 → 只改1轮
2. 改后重评分如果仍在7.5~7.8区间 → 停止改稿，标注「美妆类天然上限」通过
3. 不改第3轮——不是写的问题，是品类本身的review天花板
4. 如果总分<7.5 → 需判断是品类天花板还是写作质量问题（检查是否有情节/引语遗漏）

**注意：** 这条规则仅适用于「产品展示为主、人物叙述为辅」的美妆类素材。如果美妆素材中包含大量人物自述/个人故事（如艺人谈容貌焦虑、化妆如何改变自信），按正常长文story标准评分&gt;8分。

#### 7.5分陷阱：长文story的「内容深度」瓶颈

反复出现的模式：长文story在爆发点、情绪价值上有不错表现（各1.5/2），但**内容深度**维度始终卡在1.5/2（总分7.5/10），差0.5分过线。

**根因分析：** 正文有好的开场钩子和流畅叙事，但对路人的背景铺垫不足——原文context（时间线、人物关系、行业背景）没有充分拆解给不熟悉日本娱乐的读者。写稿时假设了读者知道「这个人在圈子里的位置」「这件事意味着什么」。

**写稿时的预防检查（写前就做，不要等review再补）：**

1. **路人测试**：去掉所有专有名词，只看骨架。第一段提到的人物/事件/群体，后文是否有至少一句话解释「谁、为什么重要、这件事的行业语境」？
2. **时间锚点**：如果是事件报道，开头是否给了清晰的时间坐标？「7月16日」或「毕业快一年了」比「近日」更有力
3. **关系链**：文中出现的人物关系（对手、后辈、前辈、合作伙伴），是否每个关系都有简单说明？例：「佐佐木美玲是日向坂46一期生，对富田来说是前辈」——不是粉丝也知道她们的关系分量
4. **跨文化透明**：日本特有的演艺圈规则（剧场公演制度、Center制、卒業文化等）是否需要一到两句背景解释？

**Review时发现深度不足的快速修复：**

| 发现的问题 | 修复方法 | 示例 |
|-----------|---------|------|
| 第一段专有名词过多 | 加一句背景锚定 | 「道枝骏佑所属的浪花男子是2021年出道的7人男团」 |
| 人物关系图未展开 | 在人物首次出现处加注释 | 「一之濑美空是2022年加入的五期生」 |
| 事件意义不明确 | 在事件描述后加一句过渡 | 「这意味着AKB时隔X年重启以歌唱力为核心的公演体系」 |
| 只有「发生了什么」没有「为什么重要」 | 在结尾前加一句事件定位 | 不升华不总结，只是延展时间线或行业位置 |

**修复原则：** 每篇加2-3处背景锚定句（合计50-100字），不重写骨架，只补透明缺口。补完后正文多50-100字，密度略有提升，但核心价值是路人友好度打分从1.5→2.0。

#### 7.5分瓶颈的另一个形态：轻量story卡「爆发点」而非「内容深度」（8/2验证）

内容深度补足之后，仍有一类轻量story素材会卡在7.5分——它们不缺背景锚定，缺的是**开头钩子**。典型是SNS晒照/配信告知/品牌联动/双人小舞台类素材，正文信息完整但开场平铺直叙（「他发了张照片」「2024年11月，某团在XX开了一场巡演」）。

**判定方法：** 评分时如果4个维度都≥1.5但总分7.5，检查是不是「爆发点=1.5」。这类素材通常有一个最戏剧性的细节可以提到第一行当钩子，且改开头不重写骨架，1轮即可过线（8/2实测3篇7.5→9.0）：

| 素材类型 | 7.5分时的平铺开场 | 第1轮修复（已验证一次过线） |
|---------|-----------------|---------------------------|
| SNS晒照（佐久间报15个后辈名字） | 「佐久间大介在Ins发了张照片…」 | 制度反差开场：「在杰尼斯这个以前后辈制度著称的世界里，能一口气报出15个后辈全名的前辈，不多。」 |
| 配信告知（日向坂魔法巡演） | 「2024年11月，日向坂46在兵库开了一场巡演…」 | 画面感开场：「舞台上没有灯光秀开场，先飞进来两把扫帚。」 |
| 品牌联动演出（五百城×奥田咖啡欧蕾） | 「出现了两位抱着吉他的乃木坂成员…」 | 反差开场：「十几人的大舞台放一边，这一次，两位成员只带了两把木吉他。」 |

**统一手法：** 把正文里最有画面感/反差感/戏剧性的细节提取为第一句（2-3行内），不是重写全篇。改完重跑renwei→重入库→重评分。**注意与「节目公告类7.5~7.9天花板」区分：** 公告类没有可提取的人物细节时才有天花板；轻量story通常有画面细节可提取，能提到第一行就提，别直接套天花板规则放弃改稿。

### 步骤4.5：评分必须落盘 score_dims（8/9强制）

**review 评分不只是输出报告，必须写入 DB 的 `score_dims` 字段。** 否则"入库→review"闭环缺最后一环，用户问"改稿循环做了吗"时拿不出 DB 证据。

**落盘格式（与历史一致）：**
- story 类：`爆点X.X/情X.X/增X.X/深X.X/标X.X|总分分|一句话理由`
  - 例：`爆点1.8/情1.8/增2.0/深1.8/标1.9|9.2分|深度评论稿结构清晰；引语丰富；信息增量极高`
- 短 news / bullet：`news-pass`
- 公众号稿（gzh channel）：`gzh去魅通过/背景锚定通过|X.X分|三维度：标题X.X/叙事X.X/适配X.X。一句话理由`
  - 例：`gzh去魅通过/背景锚定通过|8.3分|三维度：标题8.5/叙事8.5/适配8.0。行业史+选角悬念，去掉专名后骨架仍成立`（9/12 芦田爱菜稿、EBiDAN稿实作，两篇均8.3分）
  - gzh 稿同样**必须落盘**——否则中断恢复逻辑只看 score_dims 为空，会把已 review 的公众号稿当成未 review 重跑

**操作：**
```sql
UPDATE news SET score_dims='爆点1.8/情1.8/...|8.8分|理由' WHERE key='<完整40位key>'
```

**⚠️ score_dims 落盘必须直接用 sqlite3 UPDATE，禁止先用 API PUT 试（8/23 再次实测）：** 批量评分后用 `PUT {score_dims: ...}` 落盘，21/21 返回 ok 但 DB 全未更新（story 13 篇 + news 8 篇 score_dims 全空），改用 sqlite3 UPDATE 一次全部成功。与 rewritten_content 不同（8/23 同批 21/21 篇 PUT 落盘成功并经 GET 验证），score_dims 字段走 API PUT 会静默失败——评分落盘流程直接连 sqlite3 写 `UPDATE news SET score_dims=? WHERE key=?`，不要浪费一轮 PUT。

改稿循环中的每轮重评也要同步 UPDATE score_dims（覆盖旧值）。

**9/15 补充：落盘后的验证查询别用 12 位前缀做 `key IN (...)`。** `SELECT ... FROM news WHERE key IN ('cd8739984837', …)` 恒返回 0 行（DB 里存的是 40 位全键），看起来像「score_dims 全空、落盘失败」，实际是查询写错。**正确验证：** `WHERE substr(key,1,12) IN (...)`，或逐条 `WHERE key LIKE '前缀%'`。同理 UPDATE 前要先 `SELECT key FROM news WHERE key LIKE 前缀||'%'` 解析出全键再写（9/15 双日批 42 篇落盘后靠 `substr` 复核确认全部非空）。
另：`sqlite3.connect()` 之后不设 `conn.row_factory = sqlite3.Row`，`row['key']` 会报 `TypeError: tuple indices must be integers`——评分落盘脚本开头统一加这一行。

**8/9 教训：** 52 篇 review 完成后只输出了报告没落盘，用户问"改稿循环做了吗"时 score_dims 全空，闭环证据缺失。评分报告+落盘必须同时完成，缺一不可。`xhs-write-publish-flow` 的中断恢复逻辑也是用 `score_dims=''` 判断未 review 稿件——不落盘等于告诉系统"没 review"。

### 步骤5：报告输出格式

批量review完成后的输出必须按以下三层结构呈现：

**第一层：内容密度总览表（所有稿件一览）**
| 稿件 | 正文xhs字 | ja chars | 密度 | 判定 |
|------|----------|---------|------|------|
| ✅ A篇 | 1,085 | 1,272 | 85.3% | 通过 |
| ❌ B篇 | 296 | 2,842 | 10.4% | 退回 |
| ⚠️ C篇 | 1,038 | 4,209 | 24.7% | 例外候选 |

先跑全文统计再逐篇评分，让用户一眼看清哪些被退回了。

**第二层：长文story 5维度评分（逐篇）**
每篇输出格式：

```
标题: 原标题（改写标题）
正文: NNN字 | density: XX.X% | channel: xhs/gzh/both

爆发点  X.X/2  — 开头是否有钩子（附带一句话理由）
情绪价值 X.X/2  — 读者情绪反应（附带一句话理由）
信息增量 X.X/2  — 对比原文的新角度（附带一句话理由）
内容深度 X.X/2  — 路人友好度/背景交代（附带一句话理由）
标题质量 X.X/2  — 钩子+字数（附带一句话理由）
总分: X.X/10 → 通过/未达标
```

每个维度附一句话理由（如「开头直接锁定录制现场+两团私交对比，钩子有力」），不要只给数字。

**第三层：短news清单**
短news不需要5维度评分（密度+格式通过即可），但需标注通过的维度检查结果。
如果短news有异常（密度<30%、renwei拒绝、标题混入正文），单独标出。

**公众号稿件（新增）：** 不走xhs 5维度，走公众号评审标准。标注「gzh channel，去魅测试+三维度评分」。参见 `references/gzh-review-criteria.md`。
