# 小红书写稿流程

## 6阶段管道（严格顺序，不跳步）

| 阶段 | 内容 | 否决项 | 操作细节 |
|------|------|--------|---------|
| 1 | 写前准备：**先读daily review存档文件 → 拿S/A/B分级列表** → 确认key→通读content_ja→**查DB体裁字段路由（必须：curl GET → format + is_long_form）**→查关联素材→**确认关联key** | content_ja未读禁止路由；**未查DB体裁字段禁止开工**；**没读daily review文件禁止开工** | ①读 `~/.hermes/daily-reviews/YYYY-MM-DD.md`（今日review分级文件），提取S/A/B级及AKB大TOP的key和分类建议。**文件路径：** `~/.hermes/daily-reviews/$(date +%Y-%m-%d).md`。⚠️ review存档里的key前缀位数**不固定——8位、12位或14位都可能**（8/10存档用12位如69f36f3b8021，8/19存档用8位如50fd1a11，8/27存档用14位如373ef2a251afdc）。从API list dump建keymap前**先看存档文件里key的实际长度**，按对应位数匹配（`keymap[r['key'][:N]]`，N=8/12/14）。若按某一位数建map后全部NOT FOUND，**换另一位重试**（`key[:8]` ↔ `key[:12]` ↔ `key[:14]`）——不要直接判定素材缺失，8/19实测按12位建map全部NOT FOUND，换8位全部命中；8/27实测按12位建map S/A/AKB全组0命中，换14位后33/33全中。**8/20补充：targets/related字典里的前缀位数也必须与keymap统一**——若keymap键是8位而targets的related写12位前缀（或反之），症状是「主key全命中、related全部NOT FOUND」，看着像素材缺失但其实是位数不匹配：把related里每个前缀统一取`[:8]`（或与keymap相同的N）再查即全部命中。8/20实测related 15组全NOT FOUND，统一为8位后全过。同理，跨日search拿历史key建keymap时，search返回的`r['key'][:8]`与今日list的`r['key'][:8]`位数天然一致，直接合并即可。②然后执行 `references/operations-guide.md#阶段1`。③查体裁：`curl -s --noproxy '*' http://127.0.0.1:5000/api/news/<KEY> \| python3 -c "import json,sys;d=json.load(sys.stdin);print(f'fmt={d.get(\\\"format\\\",\\\"?\\\")} lf={d.get(\\\"is_long_form\\\",\\\"?\\\")}')"` — fmt=story且lf=1才按长文写**。**阶段A读素材一律用 `scripts/dump_ja.py`（read_file 会静默截断超长行）** |
| 2 | 渠道路由：xhs / gzh / both。**从review分级结果中提取gzh方向素材**，review标了gzh方向的必须先处理。**从daily-review-archive skill找到存档路径 `~/.hermes/daily-reviews/YYYY-MM-DD.md`** | — | `references/content-routing.md` |
| 3 | 编写：**写前体裁自检（7/7强制）**：先读DB确认`format`和`is_long_form`字段→`format=story`且`lf=1`则必须≥2个`##`小标题+800-1200字→**写draft时就写进##小标题，不是写完后补**→写draft到/tmp/中文稿；**标题≤20字** | 截短key / shell引号 = 无声失败 | `references/python-urllib-inline-write.md` |
| 4 | 入库：ALL_PROXY="" PUT + 三步验证 | 截短key / shell引号 = 无声失败 | `references/python-urllib-inline-write.md` |
| 5 | Review：密度检查→**加载 `xhs-content-review` skill 5维度评分**→改稿循环→达标才汇报 | 不得跳过，不得用DB分冒充 | `references/operations-guide.md#阶段5` |
| 6 | 待发布推荐（**流程最后一步**）：**5 篇 = 4 篇历史数据推荐 + 1 篇随机探索** → `scripts/pub_time_plan.py` 生成**明天** 09/12/15/18/20 预发布时间（随机偏移、禁整点）→ 落库 `xhs_pub_time`+`publish_xhs=1` | 未出数据就推荐；**触发 POST /api/trigger-publish** | `references/publish-recommendation-step.md` |

**阶段5→6 亦为铁律闭环：review 全部达标后，立即自动进入「待发布推荐」，不请示、不汇报进展。**

**阶段4→5 是铁律闭环：入库验证通过后，立即自动加载 `xhs-content-review` 开始review，中间不得插入任何其他动作——包括向用户汇报进展。向用户汇报本身也是违规。**

**写稿前必须做gzh方向检查：** review分级时可能标注了适合公众号的素材（男偶像深度分析/跨赛道内容/娱乐行业分析类）。启动写稿时，先扫一遍review的S/A级和备注，找出所有标了"适合公众号"或包含男偶像/深度分析/跨赛道内容的素材。xhs稿和gzh稿是并行路线的——不要等xhs全写完再回头看gzh，要在写稿批次开始时就把gzh方向列入todo。

**gzh 路由的判据（9/12 实作，解决「男偶像到底走哪个通道」的反复摇摆）：** 看的是**内容性质**，不是偶像性别。①review 明写「强搁置→改道公众号深度/降级」的，直接走 gzh（9/12 芦田爱菜《药屋少女》真人化：xhs 侧已连续 7 波 0 发布 ⇒ 改道公众号，写成 2295 字行业评论）；②男团/男偶像的**行业·厂牌·销量·战略**类深度素材走 gzh（9/12 EBiDAN 15周年首周105万张，2053 字厂牌史）；③男团的**粉丝争议/私物/同框/综艺花絮**类仍走 xhs（9/12 Snow Man 抽签争议、佐久间私服、SixTONES 花絮全部 xhs）——因为这类内容的目标读者就是 xhs 上的女粉丝，放公众号反而丢触达。判断口诀：**「这是给粉丝看的爆料/日常」→ xhs；「这是给路人看的人物/产业分析」→ gzh。**

**9/22 补充：成人产业/风俗/AV 相关的人物深度素材，正确处置是「改道 gzh」而不是「整个跳过」。** 9/22 的 `62b8cb0aec84`（元祖男扮女装 AV 演员的半生采访，cj2669，review 标 A 级「人物深度向新选题」）与「跳过成人产业」的既有规则冲突——两种做法各错一半：直接写 xhs 有合规风险，整篇跳过又丢掉一个完整人物弧光（提诉制作方要求下架旧作→2026 年 2 月和解→转写作并讲述行业门槛与歧视）。**判定链：①通读 content_ja；②若核心是「人物弧光/公共议题（歧视、权利、职业选择）」，只是背景落在成人产业 → 写 gzh 长文，用词回避露骨细节（「完全没有露骨画面、也不属于18禁的普通写真集」），标题与开头放在权利与歧视上；③若核心是行业操作细节/猎奇本身（如 9/21 的「0 酒精陪酒女」）→ 仍按跳过。** 同类可复用：夜店/风俗/整形题材里，只有「人」值得写、「行当的玩法」不值得写。

**6/29教训：用户明确批评了「入库后没有review」的问题。入库但跳过review = 流程不完整，属于已知违规。写稿skill的阶段5已经写明了review是强制闭环，执行时不可跳。**

## 否决项（违反即终止当前步骤，不得绕过）

0. **⚠️ 定稿提交前的日文假名自检（硬门槛，7/14强制，优先级高于一切）** — 改写稿提交入库前必须做日文假名计数检查。操作：
   ```bash
   python3 -c "c=open('/tmp/xhs_draft_xxx.md').read(); jap=sum(1 for ch in c if '\u3040'<=ch<='\u309f' or '\u30a0'<=ch<='\u30ff'); print(f'日文假名: {jap}'); exit(0 if jap<=5 else 1)"
   ```
   如果退出码=1（假名>5个），**禁止入库**。必须把正文中所有日文引语翻译为中文后再提交。
   
   **注意：这不是"格式问题"，这是高频重犯错误——用户已经纠正过4次（7/11中村丽乃→7/12渡边美里爱→7/13→7/14）。每次都是在引语中被抓。即使renwei通过、即使你认为日文原话有风味，也必须全部中文化。**
   
   **⚠️ 假名计数≠日文汉字检查（8/19新增）** — 假名计数器只覆盖平假名/片假名（U+3040-U+309F / U+30A0-U+30FF），**日文新字体汉字（発/恵/価/壱/歳/嶋/竜/徳/沢/辺/栄等）不会被计入**，renwei也不管。8/19实测：B1标题「一発合格」假名计数=0、renwei通过，但「発」是日文新字体（简体应为「发」）。**定稿提交前除了假名计数，还要扫日文新字体汉字**：
   ```bash
   python3 -c "import re; c=open('/tmp/xhs_draft_xxx.md').read(); hits=sorted(set(re.findall(r'[発恵価壱歳嶋竜徳沢辺栄広島県芸術戦争売買読]', c))); print('日文新字体:', hits if hits else '无')"
   ```
   命中后逐一替换为简体（一発→一次、広→广、芸→艺等）。标题行和正文都要查。常见高频：発（一発/発表）、広（広瀬）、芸（芸能）、戦（戦争）、売/買（売切）。
   
   **⚠️ 新字体扫描会误伤人名（9/3实测）** — 扫「嶋」时把「小嶋阳菜」自动替换成「小岛阳菜」是错的：**嶋在中文媒体固定写法的人名里保留原字形**（小嶋阳菜/小嶋真子等，见百度百科等通用写法），不转「岛」。同类还有与/国/教——简体与日文同形，扫描类若包含它们会整篇误报。**规则：①新字体扫描正则只放「与简体确实不同」的字（発広芸戦売買読選抜等），不放嶋/与/国/教这类需要按人名约定判断的；②任何自动替换后必须复查专有名词/人名（grep替换字上下文），一次性批量替换极易误伤。** 9/3实测：先误转5处小嶋→小岛，靠grep上下文复查才回滚。**9/7实测补两例：①「争」不能进扫描类——争与简体同形（争议/竞争里的争是简体正字），当年加它多半是为抓「戦争」，但戦争→战争只需换戦不换争，扫描正则含争会整篇误报；②「壱」出现在人名属固定写法保留（山本圭壱，搞笑组合极乐蜻蜓成员），与嶋同规则。命中后先grep上下文：简体常用词（争议/竞争）直接放行，人名（圭壱/小嶋/阳菜类）保留原字形，只有真正的日文新字体词（一発/広瀬/芸能）才替换。**

   **9/19 新增扫描类补漏：既有正则漏掉一批同形不同体的高频字。** 旧扫描类（発恵価壱歳嶋竜徳沢辺栄広芸戦売買読選抜）不含「強/実/気/対/経/済」——9/18+9/19 批实测：全批正文假名归零、新字体正则也显示「无」，但标题行 `她把这条路走成了最強` 漏检（強不在类里，且**标题行本来就最容易被漏**）。**扫描正则扩充为 `[発恵価壱歳嶋竜徳沢辺栄広芸戦売買読選抜強実気対経済]`；命中后照旧先 grep 上下文，人名（嶋/壱）按保留规则放行，`最強→最强` 这类一律改简体。**

   **9/19 新增假名漏网重灾区：片假名公司名/厂牌名。** `日本コロムビア` 这类公司名在写稿时极易原样落笔，出现一次＝5 个假名、两处＝10 个（c5dfe633d849 / 29195ca7c34b 首轮均 kana=10，靠终检才揪出）。**规则：唱片公司/厂牌/制作公司名（コロムビア→哥伦比亚、ビクター→胜利、ソニー・ミュージック→索尼音乐）在动笔前就定中文写法，不要等终检。**`

   **9/21 新增假名来源：罗马字+小假名混写的组合名（`Aぇ!group` 类）同样计入假名计数器。** `ぇ/ぁ/ぃ/ぅ/ぉ/ゃ/ゅ/ょ` 落在 U+3040–U+309F 区间，一个 `Aぇ!group` 出现两次就是 2 个假名（9/21 实测 `2f46e9707542` 全篇仅此 2 个、正文汉字全中文，靠终检才揪出）。**规则：这类官方名在中文稿里改罗马字化（`Aぇ!group`→`Ae!group`），不要因为「看起来是英文名」就以为不计入。**
   **9/21 另一类：单元名/人名里的单字假名极易漏。** `xhs_draft` 终检实测 `ce04d0ba9874` 单篇 8 个假名，全部来自两处——单元名「**胜手に**！四国观光大使」（`に`×2）与人名「冈田**あずみ**」（あ・ず・み×2）。修法：单元名意译（胜手に→**擅自！**四国观光大使）、人名音译（あずみ→**杏美**）、组合名罗马字化。**批量写稿时把「候选名单里所有人名/单元名先跑一次假名 grep」放在写稿前而不是终检后**——本批两次超标都是同一个机制（日文原名混在中文叙述里落笔）。

   **10/8 新增三类高频假名来源（单日批 54 条实测，共同点是「专名整体由假名构成」，写稿时极易整词照抄）：**
   ① **假名书写的队伍/单元名**：`ひなた坂46`（日向坂46 的 under 组，`ひなた`×3）在本批 story 里出现 6 次＝18 个假名，一次拉爆。**处理：定一个中文写法全文统一**——`ひなた坂46 → 平假名坂46`（点出「平假名」这个区分点），首段说明一次即可，后文全部用中文名。同类：`ひらがな` 一律写「平假名」。
   ② **Latin+假名组合名**：`Mリーグ`（`リーグ`＝3 个假名）写成中文「M联赛」；同类 `Aぇ!group`→罗马字化（见 9/21）。**规则：凡是「拉丁字母+片假名」的官方名，动笔前就定中文/罗马字写法。**
   ③ **番组名里的假名**：`《くりぃむクイズ ミラクル9》`（くりぃむ＝4 个假名）本批两篇 news 命中，`《上田と女が吠える夜》` 同源。**处理：整名意译**（くりぃむクイズ ミラクル9 → 奶油浓汤问答 Miracle 9）。
   另加人名：`宫地すみれ`（すみれ×3）→「宫地堇」。
   **一句话纪律：任何「看起来是英文名/官方名/番组名」的写法，先数一遍它含不含假名字符再落笔**，不要等 batch_precheck 的 kana 计数报错（本批 3 篇报 kana>5，全部是上述三类的漏网）。
   
   **引语处理规则：**
   - 被采访者原话中的日文 → 翻译为中文叙述，用中文引号包裹
   - 日文节目名/作品名 → 如有中文公开译名则用中文译名，无则用中文标注（如《〇〇节目》）
   - 日文专有名词（组合名、公司名）→ 用中文常见译名
   - 日文语气词/感叹（です、ね、よ、わ等）→ 全部剔除，用中文语气替代
   - **括号注音整段删除（8/24）** — 日媒在汉字名后标注读音的括号（如「川崎桜（※「崎」は正式には「たつさき」）」「山崎天（※「崎」は、ただしくは「タツサキ」）」）在中文稿中**整段删除**，不要尝试翻译或保留注音。8/24批量25篇中两处命中（e097682724fe、44c5b18ebf6e），直接删括号后假名归零。这类注音对中文读者无信息量，保留反而引入假名。
   - 唯一允许保留日语假名的场景：日语专有名词如SHOCK、October Sky、Mステ等不超过5个
   - **日文人名的替代技巧**：当正文中出现日文人名（如せいや、まえだまえだ等无可替代日文假名）时：
     - 7/20验证方案：在第一次提及后用「他/她」代称替换后续所有
     - 必须保留的场景（如引语中提到人名）→ 使用罗马字转写（如SEIYA）代替日文假名，SEIYA不会被计入假名计数
     - 演员名如桜田ひより → 可译为「樱田日阳」；角色名如こもり → 可译为「美术部的角色」
   - **日文作品名/电影名替代技巧**：如《君がトクベツ》→ 直译为《你是特别的》（可接受的目标是全假名归零）
   - **赛马名替代技巧**：如ゼンダンハヤブサ → 译为「闪电隼」（任何日文片假名专有名都可以意译）
   - **7/20验证**：43个日文假名（全部来自せいや×7+君がトクベツ+こもり+桜田ひより+まえだまえだ）通过英文化+中文译名一步降到0个
   - **7/31验证（批量补跑场景）**：renwei 全部通过的 11 篇里仍有 4 篇假名超标（8~39 个）——**renwei 完全不检查假名，假名自检必须逐篇独立执行，且首行标题也可能含假名**（标题里的曲名/方言词是最容易被漏改的）。高频来源与已验证替换样例：
     → **完整替换表（7/31–9/6 共 157 行：曲名/节目名/组合名/人名/昵称/方言词等）见 `references/kana-replacement-table-0731-0906.md`**

   **常见误区（已犯）：** 以为「」引号内的日文原话可以保留→不可以。所有引号内的日文都必须翻译成中文。

   **⚠️ 主体人名本身就是假名 → 全文饱和（9/15实测）** — 当素材主角的名字是假名书写时（中村ゆり / 川越にこ / みちょぱ类），假名会出现在**标题行和几乎每一个段落里**，靠「替换引语」清不掉，而 renwei 完全不查假名（假名计数是唯一拦截点），所以写稿时毫无感觉、只有落地检查才炸。9/15 双日批实测两例：`803372f7d0c3`（中村ゆり，标题行+正文各1个 = 2个假名 ゆ・り）、`25a7328e1ca6`（川越にこ，に・こ）。
   **处理顺序：** ①**先查 review 存档 / DB 同类素材已有的中文写法**——DB 标题 `623ce922208e` 写的是「中村百合」，直接全文统一用「中村百合」，不要自己另造译名（查法：`curl -s --noproxy '*' -G 'http://127.0.0.1:5000/api/news' --data-urlencode 'search=<片假名名>' | python3 -c "import json,sys;[print(r['key'][:12], r['title']) for r in json.load(sys.stdin)['rows'][:10]]"`。9/16实测：`search=川越` 命中 7/30 的 DB 标题「川越仁子泪洒现场」⇒「川越にこ」全库统一写作**川越仁子**，不必自造）；②存档里没有中文写法时，定一个汉字读法并全文统一（川越にこ → 川越仁子）；③改完重跑假名计数（**标题行也要数**）。批量写稿时把这条和「姓名字形核对（萩/萘、辻/过）」放同一个检查位：写稿前 grep 一遍主角名是否含假名字符，命中就在写稿时直接用中文形式。

   **sed批量替换假名的两个坑（8/6实测）：** ① 原文假名已带书名号时（如`《ちむどんどん》`），替换串不要再带`《》`——`sed 's/ちむどんどん/《心潮澎湃》/g'`会把`《ちむどんどん》`变成`《《心潮澎湃》》`双重书名号。替换串只写假名对应的中文词、不带书名号，或者替换后grep`《《`检查。② 替换串包含原文旁注释里的词会产生重复——如原文`プレ味（高级感）`，`sed 's/プレ味/高级感（Premium）味道/g'`产生`高级感（Premium）味道（高级感）`。**批量sed前先读上下文确认原文形态，sed后必须重新读文件核对替换结果（grep`《《`+通读），不能只看假名计数归零就入库**——8/6一次假名归零但文本出现双重书名号/重复词，review阶段才抓到。

   **⚠️ 扩充/改稿patch会重新引入假名（8/9批量实测）** — 假名归零不是一次性动作。密度扩充、改稿循环、加小标题等任何**向draft追加或改写文字的操作后，必须重跑假名计数+替换表**。8/9批量52篇：首轮清洗后全部归零，但为达标密度对5篇story做扩充patch时，4篇重新引入假名（高桥文哉「申し子」、伊藤百花「いともも」、丸山隆平「真面目か！」、户冢纯贵「田中みな実」、尾形贵弘「ヤジマリー/ザコシショウ」），全靠第二轮清理才归零。**根因：写扩充内容时脑子里还留着日文原文的表达，顺手就把原词写进新段落。** 对策：扩充时先想好中文表达再落笔；每篇扩充完立即跑一次假名计数（单条命令，几秒钟），不要等整批写完再查——那时候每篇都要重读才知道假名在哪。

   **⚠️ 8/15批量补充：扩充13篇中4篇中招（めめグラサン/さっくん/推し活、Gジャン、仲良しコンビ、身体絞り、二度と戻らない夏）** — 密度达标后为凑 story≥800字做二次扩充，新增段落里仍带出日文原名。另外两个隐蔽点：①**把已中文化的词在patch时改回日文**（「目黑同款墨镜」被patch替换成「めめグラサン」，因为old_string用了旧版草稿文本）——扩充时old_string必须用文件当前实际内容，不能凭记忆写旧版；②**片假名中点・(U+30FB)会被假名计数**，批量扩充后统一 `c.replace('\u30fb','\u00b7')`。修复流程与8/9相同：扩充→立即假名重计→残留词查表替换→再重计。

   **8/15变体：扩充patch的new_string从日文素材原文拼接 = 把已清理的稿子改回日文。** 黑白歌合战稿里已中文化的「金属棒/第零感/Genius」被patch写回「金属バット/第ゼロ感/ジーニアス」；佐久间墨镜稿的「目黑同款墨镜/小佐久/推活」被写回「めめグラサン/さっくん/推し活」；熊田曜子稿「第16次」被写回「第16次の」。**根因：写patch时脑子里调取的是日文素材原文（老早已读过的content_ja），不是draft当前的中文状态——patch匹配的是当前文件，new_string混入日文就等于把干净文本主动改回去。** 对策强化：写扩充patch前必须重读draft当前内容（read_file），new_string一律从draft现状的中文表达出发，禁止凭记忆从日文素材拼接；每篇patch后立即跑单命令假名计数，等全部扩充完再查=每篇都要重读定位。8/15实测该模式在22篇story扩充中出现5次以上。

**8/9批量52篇推荐：python dict替换（长词优先）而非sed** — 当需要批量清理几十篇draft的日文假名时，用一个python脚本维护`{日文原名: 中文替换}`字典，按key长度降序排序后逐key `str.replace`（长词先替换避免短词误伤，如先换「なにわ男子の逆転男子」再换「なにわ男子」）。好处：a) 一个脚本一次跑完所有文件；b) 长度降序天然规避sed的部分重叠问题；c) 替换后可立即在同一脚本内重跑假名计数输出每篇剩余数。**但dict替换不能替代人工通读核对**——8/9实测即使替换后假名归零，仍有上下文语义问题（如「渋沢」类繁体字、替换后句式生硬）需要逐篇抽查。替换字典中常见词的映射本身也可以沉淀为skill的references，见 `references/8-9-mass-kana-replacement-dict.md`。

**⚠️ dict替换的《《X》》双重书名号陷阱（8/12批量38篇：10篇中招）** — 替换表里给曲名/节目名带了《》包裹（如 `'サマーツインテール': '《夏日马尾辫》'`），但draft里这些词本身已经带《》（正文写的是《サマーツインテール》），replace后变成《《夏日马尾辫》》。**修法：** ① 替换表的value一律不写《》，让原文自带的《》保留；或 ② 替换完成后全量grep `《《` 和 `》》` 双重书名号（`python3 -c` 或 `grep -l '《《'`），用 `re.sub(r'《《([^》]*)》》', r'《\1》', c)` 一键修复。8/12教训：10篇story/新闻稿中招（58b935c7fdc4、92ac65265d20、4f39efe41e29、c6afbf83a27f、e6491ba610fd、84bd3a83815f、0c27402abd4e、4f8b35020b56、237f8c0cdae6、75474874ae13），全部靠终检grep揪出。

**⚠️ 过宽token替换的语义事故（8/12）** — 替换表里出现单字/泛化词（如 `'ちゃん': '酱'`、`'さん': ''`、`'メンバー': '成员'`）会误伤：`さっちゃん` → `さっ酱`（应为「小咲」昵称整体替换）；`自分` 类词被拆坏。**规则：昵称/人称后缀必须整词替换（`さっちゃん`→`小咲`、`丹生ちゃん`→`小丹生`），禁止把后缀拆出来单独替换。** 8/12实例：draft里`さっちゃん`被替换成`さっ酱`后靠人工通读发现再修。

**8/12批量实测：dict替换自身的四个新坑（假名归零≠替换干净）**
1. **替换值带《》→双重书名号** — draft原文已带书名号时（如《シンクロニシティ》），替换值写成《同步性》会产出《《同步性》》。曲名/剧名/节目名条目的替换值只写中文词**不带《》**，或替换后 `grep -c '《《'` 复查。8/12实测两例：野球少女鷲尾→《棒球少女鹫尾》、シンクロニシティ→《同步性》都因原文自带书名号产生双重书名号。
2. **括号注音被替换→重复词** — draft里写「元伊（ウォニ）」这类原名注音时，dict把ウォニ→元伊会产出「元伊（元伊）」。写draft时括号注音用罗马字（如WONI）或不写；替换后通读抽查括号内。
3. **裸后缀（ちゃん/くん/さん）不要进全局dict** — 全局 `ちゃん→酱` 会产出「さっ酱」这类错读（正确应为「小咲」/「さっちゃん」逐名处理）。昵称后缀按人名逐个映射，参考替换表里玉喵/地鸡喵的逐名模式。
4. **kana替换后必须重跑renwei** — 假名清理本身会引入新renwei命中：12人人名/团体枚举触发「排比三连(顿号分列)」（SASUKE 12人名单稿），改用中文间隔号·（U+00B7）一次通过；「美波前辈的话、她对团体的爱、她对这首歌的感情」式三连顿号也要拆。8/12实测4篇kana归零后renwei exit 1，全部靠第二轮改稿修复。**两遍流程：全局dict替换 → 逐篇定向修复残留（含《《》、括号重复）→ 逐篇假名重计 → 重跑renwei。** 8/12新增替换条目见 `references/8-12-mass-kana-dict-entries.md`。

**8/15新坑：替换值与原文汉字重叠 → 「波波」式重复字（假名归零但文本错乱）** — 原文「波うららかに、めおと日和」中「波」是汉字、「うららかに」是假名，dict里 `うららかに→波平浪静` 替换后变成「波波平浪静、夫妻日和」（原文汉字「波」+替换值「波平浪静」头字重叠）。同类还有「しょっぱすぎるレモネード」→「酸っぱすぎる…」（假名尾部与替换头部视觉粘连）。**规则：假名片段紧贴汉字时，替换值不要再以同汉字开头（`うららかに→平浪静` 或整体词替换 `波うららかに→波平浪静`）；批量替换后 grep 同字重复模式（`(.)\1` 双字开头）+ 重读首行标题。** 8/15实测：54篇draft首轮清理后，靠通读揪出「波波平浪静」一处并修复。

- ❌ **用截短key做PUT（7/20第N次踩坑）** — 从list端点rows取的key必须用完整40位SHA1。前16位的短key做PUT会返回 `{"ok":true}` 但不落盘（rewritten_content=''）。**入库后必须用sqlite3验证rewritten_content非空。** 详见 `references/7-20-list-key-vs-detail-key-mismatch-reverse.md`
- ❌ **related_keys写入12位短key（8/18踩坑，8/22再犯）** — 批量入库脚本里 related_keys 传了12位前缀（如 `19d7cfdbef6a`），DB实际存的是12位短key而不是完整40位。用户检查关联文章时发现key被截断。**related_keys 必须用完整40位SHA1 key（从list端点rows的 `key` 字段取），不能用 key[:12]。** 修复方法：从keymap把12位映射回完整40位再PUT `{'related_keys': ...}`，用API GET验证 `related_keys` 中每个key len==40。批量入库脚本中所有 related_keys 参数统一用 `km[k12]['key']` 全量key，禁传短key。**8/22再次踩坑：批量脚本里related_keys仍手写了12位短key，靠入库后验证输出目测到 `rel=2d6d5a36ca2c,...` 才揪出。入库验证必须加机械检查不能靠肉眼：入库后跑一条命令检查所有 `related_keys` 字段每个key len==40，或入库脚本里对每个related key做`assert len(k)==40`。修复用sqlite3 UPDATE把12位map回40位（API PUT全量覆盖风险，不用于修复related_keys）。**

**9/1第4种形态：related_keys长度≠40的"多插字符"错误（42位key）** — 手写related key时多复制/多敲字符（如 `a308fcdfbdfc596ef05dab17534b4d7c4c6c389680` 实际是42位，正确key为 `a308fcdfbdfc596ef05dab17534b4d7c6c389680`，中间多了一个`4c`），sqlite3 UPDATE落盘成功、验证时 `len==40` 检查揪出。**教训：入库后验证必须同时检查 `len(x)==40` 和「related里每个key在DB中存在」（`SELECT key FROM news WHERE key IN (...)` 反向确认），只查长度查不出「恰好40位但写错字符」的静默错误。** 9/1实作：正源司稿related写入错误key后靠 `SELECT key FROM news WHERE key LIKE 'a308fcdfbdfc%'` 查到正确key修复。

**9/17新增第5种形态：SQL LIKE 批量解析 related 时，主 key 自身会混进关联列表。** 用 `SELECT key FROM news WHERE (title LIKE ? OR rewritten_title LIKE ?) AND key<>?` 解析「同人物历史 key」时，`key<>?` 里如果传的是12位前缀，DB 存的是40位全键 → 过滤恒不生效，主 key 自己的 40 位全键被当成关联项写回 `related_keys`。症状：长度检查（每个 len==40）**全部通过**，肉眼也看不出，只有把 related 逐条展开才发现在关联自己。**修法：解析时传 `km[main12]`（完整40位）而不是前缀**；解析完再跑一次「related 里不得包含本条 key」的断言。
**同一段脚本的优先级拼接（9/17采用）：** `REL[main] = 本批同事件key(insert(0) 置顶) + 同人物历史key`，最后统一 `[:3]` 截断——本批同事件（视角分工/同源重复/系列续篇）优先级高于跨时间历史关联。

**9/5补充：跨日/跨批related素材不在当日keymap时的解析链。** 双日批次里主key的related_keys常指向**前一日或更早的key**（如9/5的亚历克→9/3旧稿756c81bb8b26、田村淳→9/4简版b6351801042a、仆青→9/1稿a7c760ad440f），这些key不在当日/两日list的keymap里，批量入库脚本解析related时直接 KeyError。**解析链：①当日list keymap（前缀匹配）→②历史旧稿固定映射HIST dict（硬编码已知旧key完整40位，如756c81bb8b2649.../a7c760ad440f3a...）→③related_keys.json（先手动收集）→④最后兜底 `SELECT key FROM news WHERE key LIKE short+'%'`。** 把兜底查库放最后，一个模糊查询解决所有"related NOT IN keymap"，不需要逐个手工找。9/5实测：脚本第一版只查keymap报KeyError 3次（756c81bb/b6351801/b20d4ff8），加HIST+DB兜底后31/31入库成功。
**9/16实测：改稿后第二次 PUT 必须重带 related_keys，否则关联被静默清空。** 首次入库 payload 带了 `related_keys`，改稿后按「只写变动字段」的习惯单独 PUT `{rewritten_title, rewritten_content, publish_mode, preselected, publish_xhs}`，related_keys 会被覆盖成空（PUT 全量覆盖语义，与 xhs/gzh 字段混写陷阱同源）。**规则：任何重复 PUT 都按完整 payload 写，related_keys 一并带上（取 keymap 的完整 40 位），写完用 API GET 反查 `len([x for x in related_keys.split(',') if x])` 确认条数没掉。** 9/16实作：6825610e3f7f 改稿重入库时带上 3 个 related key，GET 验证 rel=3 才放行。

**⚠️ 9/11实测：长会话批量入库时 API PUT 会偶发 HTTP 500 / 请求挂起（服务仍存活）。** 56篇批量入库中前48篇PUT正常，第49篇起出现一次 `HTTPError 500`、随后一次请求挂起超60s（同时 `curl /api/news?limit=1` 正常返回，说明是单请求层的问题而非服务死掉）。**对策：①批量脚本对每篇PUT加 try/except + 重试；②单篇PUT连续失败/超时，直接改 sqlite3 UPDATE 写 `rewritten_title/rewritten_content/publish_mode='rewritten'/preselected=1/publish_xhs=0`，一次成功；③验证仍走 API GET。④脚本中途抛异常会跳过末尾的 `conn.commit()`——把 commit 放在每轮 UPDATE 之后或包 try/finally，否则前面已写好的 score_dims 全部丢失（9/11实测丢掉1篇）。**

- ❌ **日文原文+中文翻译括号对照的写法（7/12重犯）** — 最常见的高频犯错模式：写作者保留一句日文原话在「」中，括号内写中文翻译。如「肩書きがすごいことになっていますが（头衔是有点夸张了啦）」这种写法。**用户明确不接受这种对照格式**。正确做法：直接把引语内容翻译为纯中文叙述，不加日文原文。例：
  | ❌ 错误写法 | ✅ 正确写法 |
  |---|---|
  | 「肩書きがすごいことになっていますが（头衔是有点夸张了啦）」 | 她说头衔听起来很夸张，但 |
  | 「今までのお仕事ではなかなか着ない衣装や色だった（以前的工作中很少穿这种衣服的颜色）」 | 她说以前的工作中很少有机会穿这种衣服的颜色 |
  
  即使你认为保留日文原文可以展示」原话风味」，用户也要求全部中文化。**唯一允许保留日文假名的场景**：日语专有名词如SHOCK、October Sky、Mステ等。出口规则：全文日文假名必须≤5个。

- ❌ **引语中日文保留过多** — 即使日文引语用「」包裹保留原话（如「舞台を観るのは大好きでした」），频繁出现也会被用户批评「日语保留太多了」。改写规则：**所有日文引语必须翻译为中文叙述**，包括引语中的人物原话。除非该引语极短且翻译后失去原文风味（如「すごい海外みたい」→「好像在国外」这样简短保留有特色的），否则应全中文。
  **PUT前自检规则**（强制，每次写入前执行）：统计正文中日文假名总数（ひらがな+カタカナ）。允许≤5个（日语专有名词如SHOCK、October Sky等），超过则退回翻译再入库。
  ```bash
  python3 -c "c=open('/tmp/xhs_draft_xxx.md').read(); jap=sum(1 for ch in c if '\u3040'<=ch<='\u309f' or '\u30a0'<=ch<='\u30ff'); print(f'日文假名: {jap}')"
  ```
  jap>5则用中文替换所有引语内的日文后再入库。

- ❌ **用错误的key映射写稿（把A素材写入B的key）** — 当手动构建key→draft映射字典时，每个key在写入前必须用API验证其实际标题和content_ja与待写入的draft一致。**7/26教训：** 手岛柚叶（key=a6a67c04...）的draft被错误写入了三浦梓（key=af61b890...）的key，因为映射字典中key复制错误。检查方法：入库前用 `curl GET /api/news/<KEY>` 查看title是否匹配目标素材。入库后用sqlite3验证rewritten_content非空。这个错误不同于「截短key」——key本身是完整40位，但指向了错误的数据行。**预防：** 从API全量list拿到rows后，立即做一轮 `key → title → draft文件` 的交叉验证，确保每个key的title与实际写入的draft标题对应。

**9/8新增：draft文件名必须用统一的key前缀位数（程序化生成，禁止手写）** — 批量写稿时手写draft文件名用了不同位数的key前缀（`draft_087f17.md`=6位、`draft_af85f.md`=5位、`draft_50db.md`=4位），入库循环按 `k12[:6]` 拼路径，20篇里2篇 FileNotFoundError 中断整批，需要二次补入。**正确做法：** 写draft时文件名一律程序化拼 `f'/tmp/.../draft_{key12}.md'`（key12取统一的前12位切片），或建 `{prefix: draft_path}` 映射时用同一个切片函数。入库循环报 FileNotFoundError ≠ 素材缺失，先 `ls` 实际文件名核对位数再补，不要重写draft。

**8/11补充：交叉验证的判定标准是「人物/事件主体一致」，不是标题文字一致。** 改写稿的draft标题（rewritten_title）几乎必然与DB原标题（title）不同——脚本对比会全部输出❌，这是预期现象，不代表key映射错。正确核对：DB title和draft标题是否指向同一人物/同一事件（如DB「浪花男子直播遭刷屏否定」↔ draft「浪花男子直播被刷"你不存在"，STARTO跨国把Meta告了」都含浪花男子+直播弹幕事件）。19/19全❌但逐条人物/事件对得上 = 映射正确，可放心入库；真正的错误信号是人物主体对不上（如DB是手岛柚叶但draft是渡边莉奈）。\n- ❌ **正文无##小标题分段** — 长文story必须分段清晰，不能一团文字。写完后先自检结构再进review
- ❌ **用 `**加粗**` 代替 `## 标题` 写小标题** — renwei会标记为「加粗滥用」，`##` 语法是干净的。6/29验证。
- ❌ **用户说"改到XX字"时自己判断某版风格不对就重写新稿** — 用户说"把A版本改到900字" = 编辑性压缩，不是重写。保留A版本的结构、叙事线、风格，仅做字数修剪。如果改完后风格从"报道"变成了"评论"，说明你重写了而不是压缩了。**回退到压缩模式，问自己：这篇和原版的区别只是字数吗？**
- ❌ 入库前自己判断这篇风格不对就推翻重写 — 你觉得风格不对可以标记观察，但不能自己决定这不是xhs标准然后凭空重写一个。入库走review确定客观分数，让分数说话。主观判断不经过review就推倒重来=替用户做决定。正确的流程：改→入库→review→如果<8分，按最低维度定向修。如果≥8分，内容质量已达标，不要再因为我觉得像评论而推翻。
### ⚠️ Patch操作时的重复行陷阱

当用patch工具在文件中插入新内容（如##小标题）时，如果old_string中包含了文件中原有的文字，patch会在插入点下方留下旧文字——导致重复行。典型场景：给draft文件的开头段落前加##小标题时，old_string既包含新插入的文字又包含原有文字，但patch只匹配替换一次，插入点下方的原行文字未被删除。

修复方法：发现重复行后，用patch的remove模式（old_string包含重复的两行，new_string只留一行）一次清除。或者先完整读取文件确认重复位置，然后用patch删除多余行。

预防：做插入型patch时，old_string只写插入点后的第一行原文（不要多带上下文），确保匹配唯一且不会留下残留。

**新增陷阱（7/30）：截断old_string引发的模糊匹配重复** — 当old_string被人为截短（只写前几个字如"表演节奏已经渐入佳"）时，patch的模糊匹配策略会匹配到更长的原文目标"表演节奏已经渐入佳境"，但替换时会把截断的new_string插入匹配开始处，导致原文残余"佳境"与新内容在拼接点重复（如"渐入佳境。入佳境。"）。修复方法：发现后完整读取文件确认重复位置，用patch精确匹配重复行删除。**预防：永远提供完整的old_string上下文（至少2个完整句子的长度），不要截短。宁可old_string写得太长，也不要太短。**

**⚠️ Patch替换会吞段落：扩充story时误把整段原文删掉（9/5批量实测）** — 给板野友美稿做扩充patch时，old_string只写了「## 说到这段时…女高中生们连连称赞」小标题一行，但new_string重写了该小标题下方的段落，结果：①原段落中「但节目播出后，社交平台上的反应却截然不同…」整段关键内容被吞（new_string没带上它）；②残留了重复的伪小标题。patch返回success、字数看似增加，只有**完整read_file重读**才发现段落丢失。教训：替换语义的patch，old_string+new_string必须**覆盖同一完整段落范围**——如果要保留某段，new_string里必须完整重写它，不能只写新内容让旧内容"自然消失"；扩充前把目标段落整段读出来确认边界，patch后立即read_file全文核对（不是只看字数/假名），确认没有段落被静默吞掉。9/5还有一次同样靠重读揪出（浅井稿整篇重写后才意识到编造背景）。

**⚠️ 扩充/改稿时"插入新段落 vs 替换旧段落"的区分（8/13实测）** — 用patch扩充draft时，如果新内容是对**已有段落的重写/扩写**（如给《心机点又怎么了》最终回稿加一段节目定位说明，内容与旧段重叠），必须把**旧段全文**放进old_string做整体替换；如果只写旧段开头几个字做old_string、new_string里塞了新段落，结果会变成"新段+旧段"并存的两段重复内容。8/13实测：old_string只用了`## 六年前从一档单发节目起家`一个标题行，new_string插入整段新文字，patch后新段下方残留旧段，需二次patch删除。**正确做法：替换语义的patch，old_string必须包含被替换段的完整文本（至少完整句子），不是只给锚点行。**

   **8/18补充：扩充新增段与已有段落「事实重复」** — 福田由爱稿扩充时新增的「审查时对方没有深挖我的职业」段，与文首已有的「我说我是拍摄模特、艺人相关工作」是同一信息点，通读时发现后整段删除。扩充新段落前先扫一遍draft已覆盖的信息点（核心引语/关键数字/职业背景只写一次），避免为拉字数把同一事实写两遍——密度虚高且review阶段会被判「跨小节重复」（见xhs-content-review 8/17村山美羽案例）。

**8/18补充：扩充时的"语义重复"（非文字重复）** — 福田由爱稿扩充时加了一段"网上还有一种声音是拿她的职业说事"，与已有段落"网上最尖锐的猜测是'因为她是那位女优'"讲的是同一信息点（职业是否被审查深挖），只是措辞不同，导致同一观点全文出现两遍，review/通读才暴露。修法：合并两段或删新增段。**扩充前重读draft全文，先列"已写信息点清单"，新增内容必须是不在清单里的新信息；同一信息点宁可改写旧段也不要新增一段。** 与8/13"文字重叠"不同：文字重叠靠old_string完整性预防，语义重复靠信息点清单预防。

**⚠️ 批量脚本改过的文件，patch工具反复匹配失败→改用python精准替换（9/3批量36篇实测）** — 当draft文件经过批量脚本处理（如 `**小标题**`→`##`批量转换、破折号批量降量、假名替换）后，再对单篇做 patch 扩充，会反复报 "Could not find a match"——即使 old_string 看起来与文件内容一字不差（引号/破折号字符可能已被脚本改动，模糊匹配对中长中文段落易失效）。9/3实测连续4次 patch 失败后才改用 python。**正确做法：批量转换后要改稿时，直接放弃 patch 工具，改用 python 单命令处理：**
```python
def rep(fn, old, new):
    c = open(fn).read()
    assert old in c, f'缺锚点: {old[:30]}'   # assert 锚点存在，失败立即知道原因
    open(fn, 'w').write(c.replace(old, new, 1))
def insert_after(fn, anchor, add):
    c = open(fn).read()
    assert anchor in c, f'锚点缺失: {anchor[:40]}'
    open(fn, 'w').write(c.replace(anchor, anchor + add, 1))
```
用**短唯一锚点**（一个短语/半句）做 replace 目标，不要贴整段长文本。每次操作后立即跑字数+假名复核，避免追加内容引入新假名或把字数顶过头。**9/3另一教训：用 python append 扩充段落时，同一篇多次 append 会累积"语义重复"风险**——扩充段与已写内容讲同一信息点（9/3伊藤百花稿重复段案例），append 前重读全文确认新段落信息不在已有段落中。

**⚠️ `**`→`##`批量转换按体裁分类（9/3实测）** — 批量把整行 `**伪小标题**` 转 `##` 时，news 稿（lf=0）也被塞进 `##` 小标题，但短news正文只允许首行标题、正文带##会被当成story结构。转换脚本需区分：story lf=1 保留正文##；news lf=0 只保留首行##、正文中的##降为普通段落（去掉##前缀即可）。9/3实测18篇news一次性误加##后二次清理。
## 批量写稿纪律

**核心纪律：用户说"开始"/"继续"/"全都写了"/"冲"后，禁止任何形式的中途汇报。全部完成后一次性输出。中间问任何问题、输出总结性汇报（已完成X篇、还剩Y篇、汇报表格）、停下来征求意见 = 全部违规。**

**7/15经验：完成一轮工作后输出已完成清单+主动问"还要继续吗"也属于违规。** 用户明确说"全部都要"时，应该沉默执行直到TODO全清零。用户不会说"别问我了"，而是直接说"你为什么不写完了再问我"。

**9/3教训：news短稿正文禁止任何分隔标题（36篇双日混批实测）。** format=news/lf=0的稿子正文不要写 `**分段**` 或 `##` 做视觉分隔——news正文只允许首行 `## 标题`，其余保持段落流。混批时若用批量脚本把 `**` 伪标题统一转 `##`，news正文也会被转成 `##`，还得二次降级回普通段落（删 `##` 前缀、保留文字），白耗整轮且标题文字容易变成游离短段。写稿时就按体裁区分：story lf=1 才写 `##` 小标题；news 一律不写任何正文内分隔标题，需要分段感用「说到XX」「另一面是」类自然过渡句。

**9/22 新增两条机械检查坑（跨日双批 35 条实测）：**
① **news draft 的首行也必须写 `## 标题`**——批量写稿时容易对 news 直接从正文开写（故事型才记得写标题行），结果入库时 `lines[0]` 把正文第一句当 rewritten_title、正文被截掉一句。写稿脚本里 story 与 news 一视同仁，首行永远 `## 干净标题`。
② **检查 story 的 `##` 个数时必须排除首行**（`lines[1:]`）：按整文件数 `##` 会把标题行算成一个小标题，出现「显示 2 个、正文实际只有 1 个」的假通过（9/22 的 e5e67887a779 / 760a671f73b2 中招，靠入库前重查揪出）。

**执行方式：Phase A 写完一批 draft 后直接跑 `scripts/batch_precheck.py --dir <draft目录> --plan <plan.json>`**（一条命令覆盖上述全部机械门禁 + body字数 + 密度 + 假名 + 新字体），不要手敲这 6 类检查——9/22 实测手敲版漏掉了「news 首行」和「## 是否算进标题行」两项。plan.json 只填 `key12 -> {fmt, lf, ja}`，`ja` 一律填主素材 content_ja 长度（合并稿不填合并分母）。

   **⚠️ 10/1 实测坑：plan.json 缺项的 draft 会被静默 SKIP，报告里的「FAIL 0」是假的。** 脚本对 `plan` 里没有的 key 只打印 `SKIP <k12> (plan 里没有这个 key…)`，不计入 FAIL，末尾照样输出「N 篇检查完毕，FAIL 0 篇」。10/1 实测：写好 7 篇新 story 后只跑了旧 plan，读到「12 篇检查完毕，FAIL 1 篇」以为通过，实际上新写的几篇一篇都没被检查；补齐 plan 条目后同一批直接暴露 7 篇 FAIL（字数/顿号/密度）。**规则：每新增一批 draft 文件，先把它们的 `key12 -> {fmt, lf, ja}` 写进 plan.json，再跑 precheck；跑完必须确认「检查完毕」的 N 等于 draft 目录里的文件数，不等就是有 SKIP。**

   **配套脚本与本批实作（10/1）：** 顿号行归零不要手改，跑 `scripts/normalize-dunhao.py <dir>`（行内第 2 个及以后的 `、` → `·`）；跨日积压批的启动判断 / 跨日去重归属 / 台账见 `references/10-01-crossday-backlog-batch-flow.md`；中文落笔长度校准、补字一次到位、结构性 patch 锚点的实测数字见 `references/10-01-length-and-patch-pitfalls.md`。

   **10/8 补：`batch_precheck.py` 的「标题 ≤20 字」是硬 FAIL，且是批量模式下第一大 FAIL 来源。** 单日批 18 篇里 15 篇标题超限（最长 31 字），远超字数/假名/顿号任何一项。根因：批量写稿时标题顺手写长（带副标题、带逗号分句）。**纪律：写 draft 首行标题时就按 ≤20 落笔**，不要等 precheck 报错再回头逐条改 15 个标题（本批为此白跑一轮批量 sed/python 改标题）。计数注意：标题算法是 CJK×1、其余（拉丁/数字/假名）×0.5，所以《SHOGUN》《NYLON》这类英文名只算半个字；含中文的标题务必数中日韩字符本身。**逐篇自查：** `python3 scripts/xhs_word_count.py --check-title "<标题>" 20`。

**9/5再犯变体+降级修复法（31篇双日混批7篇中招）：** AKB大TOP"事件型→写全文"的news（前田亚美会社员/矢方美纪/长滨睡睡/前田敦子泰餐）和A级news（青叶坂研讨会/水萌/真田十勇士合并稿）写draft时**依然带了##小标题**——原因是这些news素材信息量足、写得像长文，写稿时忘了查体裁字段。判别：**只要DB format=news/lf=0，正文一律禁止##，与内容长短无关**。修复时**不能只删##前缀**——会把标题文字变成「　从"战争机器"到"魔法少女"。」这种游离孤行，与前后文断裂。正确降级三选一：①把标题行改写成自然过渡句拼进后段开头（「这场研讨会的最大卖点是阵容，上台的全是现役成员：」「这台高达有个特别的身份转变：」）；②整段标题文字信息已冗余的直接删孤行让上下文衔接；③标题行文字并入相邻段首句。降级后必须重读全文确认无孤行（grep `^　` 开头短句）+重跑假名+renwei。9/5实测7篇用「删##前缀+孤行改写为过渡句」一次修完，重跑renwei全部通过。

### 工具调用次数上限处理（7/5教训 + 7/14批量效率优化）

当批量写稿任务≥6篇时，单次会话的工具调用次数（~9-10轮）可能不够完成全部稿件的写稿→renwei→算密度→入库→验证闭环。此时：

#### 核心效率优化：先用三阶段模式替代逐篇闭环

**默认流程（逐篇闭环）：** 写1篇 → renwei → fix → renwei 验证 → 入库 → 下一篇。每篇消耗2-4轮，6篇即12-24轮，必超限。

**批量效率模式（推荐，≥5篇时强制使用）：** 把流程拆为三个独立阶段，在工具限制内最大化产出。

| 阶段 | 操作 | 工具轮消耗 | 目标 |
|------|------|-----------|------|
| 🅰 写稿阶段 | 一口气读完所有content_ja → 一个接一个写所有draft到/tmp/（跳过renwei）→ **每写完一篇story draft立即做字数检查（<800字则就地扩充）** → 扩充参考 `references/story-draft-under-800-expansion.md` | ~3-5轮 | 产出全部draft，且每篇story字数达标 |
| 🅱 审读阶段 | 对所有draft批量逐篇跑renwei → 统一修 → rerun | ~4-6轮 | 全部renwei通过 |
| 🅲 入库+review阶段 | 全部入库→密度计算→验证→逐篇5维度review | ~6-8轮 | 完成落地 |

**优点：** 每个阶段都是完整的batch产出。即使阶段C中断在工具上限，也已经准备好了全部draft在/tmp/和全部renwei通过状态，不会出现"这篇写了一半没入库、那篇入了库没review"的碎片状态。

**批次A的素材读取模式（9/16 实测 26 篇，3 次终端调用读完全部素材）：** 不要逐篇 `read_file`（40 篇=40 次调用）。①先用一个脚本把全部目标 key 的 `content_ja` 落到 `/tmp/mat/{key12}.txt`，**并在同一循环里打印 `ts / format / is_long_form / cj_len`**——体裁字段判定与素材长度规划一步到位（list dump 的 rows 自带这三个字段，等价于逐条 curl 查 DB）；②随后按 4–6 篇一组打印：`python3 -c "for k in ['k1','k2']: print(open('/tmp/mat/'+k+'.txt').read())"`，**主素材全文、关联素材截断到 700–1100 字**（主素材通读 + 关联 scan 补事实点，正合同源重复合并的读法，也省一半上下文）。
   ③落盘脚本同时断言 `len(key)==40` 全通过，避免后面入库拿到截短 key。

**批次A的落盘模式（9/12 实测33篇，比逐篇 write_file 省一半轮次）：** 用一个 `terminal` 调用 + python heredoc（`cd /tmp && python3 - << 'PYEOF' ... PYEOF`，**分隔符必须加引号**，否则 shell 会吃掉正文里的 `$`/反引号）一次性写 4-8 篇 draft：脚本内维护 `D = {'<key12>': "## 标题\n\n正文..."}` 字典，循环 `open(f'{DRAFT}/xhs_draft_{k}.md','w').write(v)`，**并在同一个循环里立刻打印每篇的 `body_chars` 与 `##` 计数**——这就是「每写完一篇 story 立即做字数预检」的机械执行方式，不需要额外再跑一轮检查命令。9/12 用这个模式 5 个调用写完 33 篇，当场发现 2 篇 story 不足 800 字（794/537）就地修掉，Phase C 零返工。若 `execute_code` 在当前 profile 被策略拦下（cron/approval 模式），直接走这条 heredoc 路径，不要在写稿中途停下来找工具。

**story 稿的 `## 小标题` 必须在 heredoc 的字面文本里就直接写 `## `**（不是 `###`、不是 `**加粗**`）——批量模式最容易在这一步偷懒，等 Phase B 才发现要整批降级就要多跑一轮假名+renwei。

**⚠️ 注意：** 阶段A读content_ja时要一次性读取全部key的素材，不要每篇单独curl。用 `curl -s --noproxy '*' '.../api/news?date_from=...&limit=200'` 拿到全量rows后，用python一次性筛选出目标key的content_ja保存到各自/tmp/文件。

**⚠️ 阶段A的密度前置规划（7/28经验）：** Story lf=1 的「字数≥800字」和「密度≥30%」是两个独立的门槛，对深访类素材（content_ja > 2000字）可能互相冲突。700-800字长文可以满足字数门槛，但密度只有13-20%。**写前预判content_ja长度，提前规划目标正文长度：**
- content_ja ≤ 1500字 → 800字正文即可达标密度
- content_ja = 3000字 → 需写约900字正文（30%）
- content_ja = 4000-5000字（深访/长文盘点类）→ 需写1300-1500字正文才能达标密度（8/17实测：SPEED盘点4591字写1290字仍28.1%、藤原宏访谈4242字写938字仍22.1%——story 800字门槛对这类素材不够，Phase A必须直接写足到30%，不要只满足800字就开工）
  **扩充余量原则（8/17恢复实测）：目标正文=ja_len×0.31~0.33，不要卡30.0%。** 落笔字数几乎总比预估短——藤原宏4242字目标1273，实际三轮patch才过线（1157→1235→1266→1294，29.8%→30.5%）；SPEED写1411字才稳过30.7%。压线稿（30.0-30.9%）在后续改稿删字时最容易跌破，首轮就按×0.32规划，一次写足，别留多轮扩充尾巴。
- content_ja = 5000+字（深访类）→ 需写1500+字正文才能达标密度
- content_ja ≥ 8000字（万字深访）→ 需写2500-3200字正文才能达标密度（8/10实测：10681字深访写3170字→30.1%；review若标「可分2篇」但用户未确认拆篇，就单篇写足到30%，不要停在20%档）
写一个5000字深访的650字版本纯属浪费素材——必须充分挖掘引语、背景、细节写够字数。**在Phase A动笔前，先快速算一下ja_len，如果ja_len > 2000，确定目标正文长度后再写。**

**⚠️ 批量含深访时Phase C超限截断（8/17实测）** — 27篇批量中混入2篇4000+字深访，Phase A只写到800字、把密度扩充留到Phase C，导致Phase C在工具调用上限内被截断（2篇扩充版未重入库、review未跑、score_dims未落盘）。**规则：批量中含任何ja_len>3000的素材，Phase A就按目标密度写足正文（见上表），Phase C只做入库+验证+review，不给密度扩充留尾巴。** 截断恢复路径：draft都在/tmp/，DB里rewritten已写入旧版，只需重写扩充版→重入库→重跑review，不要重开整个流程。

  **8/24重犯（3篇live report）** — 25篇批量中3篇大型演唱会/卒业式report（5402/5754/6519字）在Phase A只写到998-1773字（密度17.6-28.3%），把密度扩充留到Phase C，又一次在工具上限处截断。**规则：ja_len>3000的素材无论类型（深访/live report/卒业report）一律按 ×0.31~0.33 规划目标正文长度，禁止只写到800-1000字就把密度问题留给Phase C。** 中文落笔长度普遍比自估短 40~60%、补字必须一次 ≥150 字的实测数字与修法见 `references/10-01-length-and-patch-pitfalls.md`。

  **ja>3000 素材（live report/深访/长文盘点）累计第4次重犯** — 首轮就按 `max(800, ja×0.31~0.33)` 写足（中文落笔比直觉低约40%），别只写 800–1130 字把密度留给 Phase C（8/24、8/31、9/28–10/1 三次撞工具上限）。见 `references/9-28-to-10-1-crossday-4day-batch-flow.md`；顿号清理 `scripts/fix_dunhao_lines.py`。

**批次台账：** 10/2–10/4 46 xhs+2 gzh+6 bullets+28 merged（`references/10-02-to-10-04-crossday-3day-batch-flow.md`）；10/5 单日批 10 story+8 news+9 bullets+4 merged（`references/10-05-single-day-batch-flow.md`）；10/7 单日批 14 story+4 news+19 merged（`references/10-07-single-day-batch-flow.md`）；10/8 单日批 9 story+9 news+8 bullets+9 merged（`references/10-08-single-day-batch-flow.md`）。

#### 10/1 批量级纪律与新增坑（详见 `references/10-1-batch-scale-discipline.md`）

跨日检查显示多日未写时，**开批前先把逐日 target 数加总**：总 target > 60 或未写日 ≥ 3 天
→ **单日闭环、逐日推进、绝不交错**（day N 的 写稿→precheck→renwei→入库→review→score_dims
全部落盘后才开 day N+1，最新一天优先）。理由：draft 只在 /tmp/，DB 是唯一持久层，先写完
多日 draft 再统一入库，撞上工具上限就会整批滞留 /tmp 且 DB 无痕。做不完就如实报天数。

- **阶段A 读素材一律 `python3 scripts/dump_ja.py <date> <前缀...>`** —— `read_file` 对超长行
  静默截断（~2000字/行），裸读 content_ja 会丢掉中后段引语且不报错。
- **批量补丁脚本禁止 `assert`/裸 `open()`**：一处抛错会中止整个 heredoc，其后补丁静默丢失。
  改 `print('MISS'/'NOFILE')` 继续；文件名 key 必须是**完整 12 位前缀**，写短了 precheck 输出
  `SKIP` 且不计入 FAIL——每次核对「检查完毕 N == draft 数」。
- **字数靠写后实测**：中文成稿比直觉估计低 25~30%；目标 `max(800, ja_len×0.31)`，
  每写 2~3 篇立刻跑一次 precheck，不要攒到整批末尾。
- **顿号行是 news 第一大 FAIL**：并列人名/曲名列表（最多 5~6 个名字那种）写稿时就拆句或换
  「和/以及/等人」；同行第二处顿号也计数。
- **renwei 假阳性**：①「的+路」格言公式会命中 `走了相反的路`/`在演员这条路上`，**`##` 小标题
  也中，标题行必查**；②「不是X而是Y」会命中「既不是…也不是…」（改「既没有…也没有…」）。
- **`##` 标题下不要留独行导语短句** → 触发短句轰炸，并进下面的正文段。
- **跨日同一事件只在更晚/更全那天成篇**，另一天挂 `merged-into-<主条key12>`；被吸收为 related
  的副条保持 `preselected=0`（预期状态，不是漏写）。
- 假名新增对照见 `references/10-1-mass-kana-dict-entries.md`；`おいしいのつくりかた` 误写
  《美味作り方》会命中假名（`り`），凡曲名夹单字假名必须整词意译。

#### 单篇闭环仍然适用的情况

当batch size≤4篇时，或素材间差异大（混合了story/长文/短news/多个不同事件），走逐篇闭环更自然——每篇完成renwei→入库后再写下一篇。

#### 追加写稿模式（Batch追加，7/23经验）

当主batch写稿完成后，用户追加指定2-3篇素材「也要写」时，走**追加模式**：

**追加模式流程（简化版，跳过批量前置检查）：**
1. **直接通读追加素材的content_ja全文** — 不需要重读daily review文件（已经在首次启动时读过了）
2. **查DB体裁字段**（format+is_long_form）— 此步骤不可跳过
3. **写draft → renwei → 入库 → review** — 逐篇闭环（因为追加篇数少，走逐篇效率更高）
4. 追加稿的review标准与主batch相同（story lf=1需≥8分）

**追加模式 vs 首轮批次的区别：**
| 维度 | 首轮batch | 追加模式 |
|------|-----------|---------|
| 读daily review | 必须 | 跳过（已读） |
| 查全量同人物DB | 必须 | 可选（素材已确定） |
| 聚类复查 | 必须 | 可选 |
| 写稿方式 | 三阶段批量 | 逐篇闭环 |

**注意：** 追加模式不等于跳过体裁判断和review。追加稿仍要查DB的format+is_long_form字段确认体裁，入库后仍要跑review。密度不够时走同样的扩充/豁免规则。

### 「全部写」= 直接动手，不选不请示（7/24新增）

当用户对公众号方向说「全部」时，含义是所有S/A级中适合公众号方向的目标赛道素材全部写——不是让你从中选几篇问用户意见。跳过此步直接执行。

**「你要哪篇还是我帮你选」是被骂的句式。** 用户从未对这种提问有过正面回应——要么自己默默选完写好，要么全部。直接动手比征求意见更符合这个用户的工作流。

### 用户查的是已存在的结果，不是要你重新跑（7/24新增）

当用户问「XX做了吗」/「结果呢」时：
1. **第一反应是查已存档的文件或数据**，不是重新执行流程
2. 检查 `~/.hermes/daily-reviews/YYYY-MM-DD.md` 是否存在？存在就直接 `read_file` 给用户
3. 文件不存在再确认是否要重新跑
4. **不要对用户说「跑完了但没投递过来」这种推测性结论**——如果文件不存在，就是没有跑完或没有跑成功，不是「跑完了但输送丢失」

**用户厌恶的两类推定：**
- 推定「已经做过的」是「需要重做的」——用户查review结果，你第一反应是跑新的，等于说之前的白做了
- 推定「需要征求许可」的是「可以默认执行的」——用户说「写公众号」，按全量生产执行，不是先问先选

### 中断恢复

1. **不要慌**。完成当前阶段后输出已完成/未完成清单
2. **继续流程**：用户说「继续」后，恢复处理
3. **review衔接**：如果中断时部分稿件已入库但未跑review：
   - 从DB拉取所有已入库稿件（preselected=1 AND rewritten_content≠'' AND date_from=当天）
   - 筛选出 `score_dims=''` 的稿件（未跑review的标记）
   - 逐篇跑review评分
   - **8/17恢复实测的机械检查链（评分前全部通过才评分）：** ①假名≤5（含标题行）→②story查##小标题≥2/无### →③字数≥800（story）→④密度≥30%（4000+字深访按扩充余量原则规划）→⑤标题≤20→⑥renwei exit 0/2。任一不过：先修→sqlite3 UPDATE重入库→API GET验证→再过链。
   - **合并稿关联key验证：** 合并时被吸收的key（related_keys指向的那些）保持 presel=0、rw=False 是预期状态——主key承载内容+related_keys，恢复时无需处理关联key，别误当成"漏写"。
4. **Phase C 从未开始（draft 在 /tmp、DB 全空）恢复（7/31 实测）**：中断发生在「Phase A+B 完成、还没入库」之后（典型：停在请示式提问被会话重置，用户次日追问"是不是没走改稿循环"）。此时 DB 的 rewritten_/wechat_ 字段全空、preselected=0、无评分。按此顺序补跑完整 Phase C：
   - ① 确认 draft 文件都在：`ls -la /tmp/xhs_draft_*.md` + `find /tmp -name "xhs_draft_*.md" -newermt "YYYY-MM-DD"` 按日期核对（注意 /tmp 里可能有前几天的旧 draft，只取当天）
   - ② 从 API list dump（`date_from=当天&limit=200`）提取完整 40 位 key → draft 映射，禁截短
   - ③ **全量假名自检（含首行标题）**：renwei 通过 ≠ 假名≤5。7/31 补跑 11 篇里 4 篇假名超标（8~39 个），全是曲名/方言词/昵称/乐队名。先修完再入库
   - ④ 入库：gzh→sqlite3 UPDATE wechat_字段；xhs→rewritten_字段+preselected=1+publish_xhs=0；合并稿互设 related_keys
   - ⑤ API GET 验证非空（防静默失败，7/31 实测 12/12 OK）
   - ⑥ 密度计算 → ⑦ 5维度/公众号三维度 review → ⑧ 改稿循环 if-then
5. **分断点选择**：尽量在一个阶段的末尾自然中断（所有draft写完 / 所有renwei跑完），不要在写一半的稿件处中断

### 写稿批次中杜绝素材遗漏（7/1教训）

**用户问「这篇不需要写吗？」= 你把素材遗漏/跳过了。** 当review分级输出有S/A/AKB大TOP多个级别，用户说「全部都要」或「A级素材继续」时，以下步骤缺一不可：

1. 从API拉 `date_from=今天&limit=200`，拿到全量列表
2. 对照review输出，找出**所有**S/A/AKB大TOP的key（不要只靠记忆或query过滤关键词——关键词过滤可能漏掉ts=5.0、tags不匹配主流关键词但确实在A级内的素材）
3. 写一个完整列表（key+title+ts+fmt+lf），逐条核对：这条写了吗？为什么没写？如果因为聚类合并跳过，明确标注理由
4. 把未写过的素材全部列出来给用户确认，或者在用户说「继续」时确认全部覆盖

**常见遗漏原因：** 花田蓝衣ts=5.0 story lf=1但tags=「铃木收,AKB48,花田蓝衣,DH」——关键词过滤query都没命中，被静默过滤掉。**补救方法：** ts>=4.5 的story全纳入，不依赖关键词匹配。

### 跨日批次覆盖检查（8/1教训：用户问"7-31日的素材还没有写稿吧"）

**⚠️ 当日review未跑时的写稿模式（8/13实测）：** 用户说"开始写稿"时如果当日 review 存档不存在（cron 未触发，如 8/13 cron last_run 停在 8/12），**不必停下来等 review**——直接在主进程做第1+3层（全量扫描+聚类分级+跨时间关联）作为写稿依据，完成写稿入库+review 后，再补跑完整四层 review 存档（第4层发布数据回顾可以在写稿完成后补）。8/13 实作：L1/L3 先行→23篇写完入库→用户说"daily review补齐"→补第4层+存档+审计+segment-send，全部闭环。关键：写稿时就把聚类/分级/关联结果整理好（key+title+ts+fmt+合并组），补存档时直接复用，不重复拉数据。

**用户说"开始写稿"时，启动动作除了读当日daily review，必须同时检查两个跨日维度：**

1. **前一日素材是否已写？** 查询前一日 `date_from/date_to`，统计 `preselected=0` 的条数。**整批漏写的判定信号（9/22 实测）：前一日全部行 `preselected=0` 且 `rewritten_title`/`rewritten_content` 皆空、同时 `references/` 下没有对应那一天的批次文件**（最近一份批次 reference 停在前一天）→ 判定为漏写日，整批纳入本轮，并按 review 日拆两个子批、**先当日再前一日**各自走完整 A→B→C（照 9/3 教训）。9/22+9/23 两日合计 52+35 条，拆批后 35 条落地、零遗漏；不要因为「量太大」就只写当日（8/1 教训：用户会直接问「7-31 的素材还没有写稿吧」）。如果前一日 review 存档存在（如 `~/.hermes/daily-reviews/2026-07-31.md`）但素材全部未写（64条全 preselected=0），必须把前一日批次纳入本轮写稿范围，不能只写当日。**8/1实作：我只读了当日 review 文件（2026-08-01.md）就开写，用户追问才发现7/31的64条素材一条都没写，需要整批补写10篇。**
2. **review之后是否又有新素材入库？** daily review 文件覆盖的 total 条数 ≠ 当前 API total 时，说明抓取侧在 review 之后又入库了新素材（8/1：review 01:43 覆盖34条，02:00 又入库24条——西畑大吾死神×6、向井康二×5、Snow Man TFT、黑木康正等）。这些 post-review 素材不在分级文件内，写稿前列出并与用户确认，或按同事件聚类（死神×6/向井×5明显成簇）自行合并处理。

**操作：** 写稿启动时用 `curl /api/news?date_from=<前一日>&limit=200` 和当日各拉一次全量，输出「已写（preselected=1）/未写（preselected=0）」对照，未写清单里排除垃圾标题（含"我的标题/标题规则/生成的中文/重复了/引流摘要"等），剩余的就是跨日待补范围。参考 `references/8-1-cross-day-batch-coverage.md`。

**9/7效率技巧：list dump 的 rows 自带 `rewritten_title`/`preselected`/`publish_xhs` 字段——判断前一日批次是否全部入库，直接一条 python 遍历 dump 即可（`preselected==1 and rewritten_title非空` = 已写），不需要逐个调 detail 端点验证。** 9/7实测：拉9/6+9/7两天合并list（108条）后一次遍历确认9/6全部13条（S3+A8+AKB2）已入库，当日9/7的51条全未写 → 确定只需写当日批次。跨日检查与当日keymap建立合并到同一次dump（`date_from=前一日&date_to=当日&limit=300`），省一次API往返。

**⚠️ 9/17实战：`preselected!=1 or rewritten_title为空` 的行不等于「漏写」——先过三张三态表，再决定是否补写。** 9/17 启动时遍历发现 9/16 有 33 行「未写」，逐条核对后确认 0 条遗漏，全部属于下面三类：

| 形态 | DB 特征 | 判定 |
|------|--------|------|
| AKB大TOP bullet（晒照/表纸/summary bullet） | `preselected=1` + `rewritten_content` 为空 + `score_dims='akb-top-bullet'` | 已按规则处理（只入库不写正文），**不是遗漏** |
| gzh 改道稿 | `preselected=0` + `channel='gzh'` + `wechat_content` 非空 + `rewritten_content` 空 | 已入库到 wechat_ 字段，**不是遗漏** |
| 上一批主动跳过项 | 什么都不设，但**上一批的 `references/<M-D>-*-batch-flow.md` 末节「跳过的条目」有记录** | 按上批决策跳过，**不是遗漏** |

因此启动动作要加一步：**除了读当日 daily review，还要读最近一份批次 reference（`references/<M-D>-single-day-batch-flow.md` 之类）的「跳过的条目」节**——它是上一批范围决策的事实源，只看 DB 三字段会误判成整批漏写、白跑一轮（9/17 差点把 9/16 的 9 条已决策跳过项 + 2 条 bullet 当遗留补写）。

**⚠️ 8/30教训：`date_from=<前一日>` 会把后一天的素材也带出来——不要误判为「post-review 未分级新素材」。** 8/30写稿启动时 `date_from=2026-08-28&limit=200` 返回116条（8/28存档只覆盖57条），多出的59条一度被当成「review之后又入库的未分级素材」。实际这59条全部是8/29的素材：API的 `date_from` 是含起点、`date_to` 未设则无上界，查询天然跨两天。**判别方法：把「多出来的key」与当日及次日两个review存档的key前缀逐一比对——如果全部命中次日存档（或本日存档），就是日期边界导致的重复拉取，不是漏分级，直接按存档名单写稿即可，不要为主进程补分级浪费时间。** 只有真正不在任何存档里的key才是post-review新素材。

3. **当日 review 存档缺失（cron 未跑/被跳过）时的写稿启动路径（8/13实测）** — 用户说"开始写稿"但 `ls ~/.hermes/daily-reviews/$(date +%Y-%m-%d).md` 不存在、最新存档停在前一天时：
   - 先 `cronjob action=list` 查每日review job 的 `last_run_at`。若 last_run_at 停在更早日期（8/13 说开始写稿但 last_run_at=8/12 01:42，而 job 是每日 01:30），说明当日 cron 未执行、当日素材无分级——不是"没素材"，是"没 review"
   - **不要停下问用户"今天是哪天的review"**。用户说"开始写稿"已授权流程，写稿前置的分级由主进程补跑：第1层（全量扫描+聚类+S/A/AKB分级）+ 第3层（`search=` 跨时间关联），产出分级清单后直接进入写稿
   - 第2/4层（价值建议/发布数据回顾）留给正式 daily review cron 补齐，写稿侧不需要
   - 8/13 实测：53 条当日无分级，主进程补跑第1/3层后完成 23 篇。**10/7：存档是「抓取故障报告」（写 0 条、无 S/A 清单）时先核对 DB `count(*) WHERE date(created_at)=当日`——10/7 存档写 0 条、DB 实有 59 条（01:42 已恢复），照单信会白等一天。**

**⚠️ 跨日批次的keymap必须合并两天list（8/12教训）** — 写8/11的素材时，如果只用当日（8/12）list建keymap，前一日16个key会全部`NOT IN LIST`。正确做法：`keymap = {r['key'][:12]: r for r in rows_today + rows_yest}`（合并两个list的rows），8/11素材用前日list的完整40位key入库。**key→draft交叉验证也要覆盖跨日：** 8/12当日22篇在今日list验证、8/11的16篇必须用合并keymap验证，逐条核对「人物/事件主体一致」后再入库。

### 跨日双批次≥30篇：按review日拆两个≤20篇子批，各自走完整A→B→C闭环（9/3实测36篇教训）

当跨日覆盖检查发现**连续两天素材全部未写**（如9/2存档59条+9/3存档57条全preselected=0），S/A/AKB合计可达36篇。三阶段批量模式（写稿→renwei→入库）能一口气跑完36篇，但**Phase C的逐篇5维度review会在工具调用上限处被截断**（9/3实测：36篇全部写稿+renwei+入库完成，review未开始就超限）。对策：

1. **拆批**：按review日拆成两个独立批次（9/3批18篇、9/2批18篇），每批内部走完整「写稿→renwei→入库→逐篇review」闭环
2. **先跑当日批**（最新review日），再跑前一日批——当日批review完成后再启动前日批写稿，保证至少最新批次完整落地
3. **不要把两日draft混在一起攒到Phase C才review**——36篇review+改稿循环远超单会话工具预算
4. 中断恢复时draft全在/tmp、DB已入库，按「中断恢复」第4条从review补跑即可

### 批量写稿中的review结果复查（6/28教训）

daily review的分级结果可能把同事件素材同时列为S级和A级（如THE MUSIC DAY 42人混搭= S级，同事件高桥海人×森本= A级）。写稿前应复查聚类：

- 如果review已聚类标注「同事件」，但S/A级里都有同事件条目 → 保留S级，A级直接cancel
- 不要在S级写完后才发现A级是同一个事，白写一篇
- 复查方法：写稿前扫一遍所有assign的key的title/tags/聚类标注，看是否有重复事件

### 路由可被用户中途改变（6/30教训，7/1更新入库规则）

review中标注为「S级→小红书写稿」的素材，用户可能在写稿过程中要求改路由为公众号格式。这不是验证错误，是用户的正常决策调整。处理方式：

1. 小红书key已有已入库的rewritten版本 → 不动DB的rewritten_字段，公众号稿写入同一条记录的 **`wechat_title` / `wechat_content` 字段**
2. 设置 `channel='gzh'`、`wechat_publish=0`、`preselected=0`
3. ⚠️ **致命陷阱：API PUT是全量覆盖，不是增量更新**。如果先写入了小红书rewritten_字段，再单独PUT wechat_字段，第二个PUT会清空rewritten_字段（因为PUT body里没带上rewritten_字段的值）。**正确做法：**
   - **方法A（推荐）**：用python读当前state，合并成一个payload一次PUT（参考`references/dual-channel-merge-pattern.md`）
   - **方法B**：小红书字段走API PUT，公众号字段走sqlite3 UPDATE直接写DB
   - **绝对禁止**：分两个单独PUT调用分别写不同字段 —— 第二个PUT会静默覆盖掉第一个
4. 公众号稿走独立的review流程（去魅测试+renwei+公众号标准），不和小红书review混用
5. 参考 `references/dual-channel-merge-pattern.md` 和 `references/6-14-gzh-write-to-db.md`
6. **公众号稿的存储位置不是workspace**：写入DB的`wechat_title`/`wechat_content`字段，`channel='gzh'`。发布脚本`wechat_publisher.py`优先读wechat_字段。参见`references/workspace-vs-db-gap.md`。

### 同日输出xhs版+gzh版双版本（7/10经验）

当用户对同一素材要求同时输出**小红书版（编辑性压缩）** 和**公众号版（长文自由发挥）** 时：

1. **xhs版**：用户说"改到900字" → 保留原版本结构、叙事线、风格，做字数修剪
2. **gzh版**：用户说"字数不限" → 1500-2000字，带##小标题，可加入更多背景/细节/情感层次，叙事完整
3. 写入DB：`channel='both'`，一次PUT同时设`rewritten_title`/`rewritten_content`（xhs）和`wechat_title`/`wechat_content`（gzh）
4. 先读当前state合并payload，防止全量覆盖（一个PUT调用同时写两套字段）
5. xhs版和gzh版走各自的review渠道：xhs→5维度评分，gzh→去魅测试+三维度评分

**文案差异：** xhs版更精炼（hook在前、引语精简、每段推进快），gzh版更叙事完整（场景铺垫、人物背景展开、时间线拉长）。不要写两个同样结构同样内容的版本。

当多篇同人物/同事件的小红书素材需要合并为**一篇公众号长文**时（典型场景：用户说"这几篇合并发公众号"），走独立流程：

**适用条件：** DB中有同一人物的多条入库记录，其中至少1条有content_ja正文

**流程：**
1. **找出所有关联key** — 用API `search=` 搜同人物，列出所有入库记录
2. **通读各素材content_ja** — 确定每篇对应的新闻事件和时间顺序
3. **判断合并角度** — 时间线叙事 / 人物对照 / 行业分析
4. **写gzh长文草稿** ~1500-2000字，带##小标题
5. **renwei审读** — 公众号稿renwei典型拒绝模式：结尾「写在后面」段 → **直接删整段**；「这折射出一个事实」过渡句 → 删除标记
6. **公众号review** — 去魅测试 → 背景锚定 → 三维度评分（合格线7分）
7. **写入DB** — `wechat_title`/`wechat_content`，`channel='gzh'`，不覆盖xhs字段

**⚠️ 共存规则：** xhs稿已入库后，gzh稿用`wechat_`字段+sqlite3 UPDATE写入，不走API PUT（避免全量覆盖）。参考`references/dual-channel-merge-pattern.md`和`references/7-5-gzh-merge-kamenashi-tanaka.md`。

### ❌ 常见错误：把长文story写成评论/分析/普世升华（7/1花田蓝衣教训）

用户指明"xhs版本改到900字，按长文标准"时，**写了评论/分析/普世升华 = 写错了**。xhs长文story和公众号长文的根本区别：

| 维度 | xhs长文story ✅ | 评论/分析/升华 ❌ |
|------|----------------|-----------------|
| 主角 | 事件中的人物（名字+细节） | "一个21岁的女孩"/"这个年轻人"（匿名化） |
| 叙事方式 | 场景、引语、画面感 | 抽象规律、普世启示、总结 |
| 引语 | 直接引述当事人原话（"她说……"） | 间接转述"她承认了错误" |
| 结构 | 事件经过→细节→引语→后续 | 提出观点→论证→举例→结论 |
| 信息密度 | 具体时间、地点、对话、数字 | 概括性描述、传播学概念 |

**自检方法**（写入前问自己）：
1. 这篇文章去掉专有名词后，是一篇具体的新闻报道，还是一篇通用的心灵鸡汤/社会评论？
2. 读者能说出"这个人做了什么、说了什么"的具体细节吗？
3. 有没有至少3处直接或间接引语？有具体的时间/数字信息吗？
4. 文章读起来是一篇"报道"还是一篇"读后感"？

如果答案是"鸡汤/评论/读后感"→ **这不是xhs长文story，重写。**

**用户指定字数时的规则：** 用户说「改到900字」时，目标就是900±100字。即使素材大、信息多，也要控制在目标字数附近。不超不限。「长文标准」≠「字数随便写」——900字的长文story是浓缩版的报道，选中一个核心里写深，不是把全部素材灌进去。

**900字中长稿压缩模式（7/11中村丽乃案例）：** 当用户对已入库的story长文（原始~1100字）说「改到900字左右」时，走以下流程：
1. **保留骨架**：保留关键叙事节点（开场金句、逆袭事件、核心引语、高潮场景）
2. **砍冗余描述**：删除不必要的过渡句、重复情绪表达、次要背景
3. **合并短段**：将4-5个小节压缩为3-4个，个别小节合并
4. **日文全部中文化**：这是压缩的好时机——同时做「日文保留过多」修正，把所有日文引语翻译为中文
5. **补充信息厚度**：压缩后如果字数偏低（700-800），用素材中的真实细节（帝剧着到板、交响乐团配乐等）补到目标附近，不做空洞填充
6. 最终验证：字数达标、日文假名≤5、renwei exit 2

**9/21 补充：这条同样适用于「事后指定重改」——用户翻看过往批次的待发队列，挑一篇说「这个有价值，需要按照长文在900字左右」。执行要点（本session两连发：秋元康稿 1093→941、台风稿 1132→935）：**

| 项 | 规则 |
|----|------|
| 体裁先行 | 动手前查 DB `format`/`is_long_form`。`story/lf=1` → 保留并补齐 `##`（≥2个）；**`news/lf=0` → 用户口中的「长文」= 段落流的完整报道，正文一律不加 `##`**。体裁只认 DB 字段，不认用户话里的「长文」二字（否决项0）。**并在回复里明说这个差别**——用户会以为两条都该带小标题 |
| 字数口径 | 目标字数一律用 `scripts/xhs_word_count.py` 测，与历次汇报口径一致。**renwei 报告里的 `(xhs: N)` 是另一套计数，比脚本小 60~140 字**（9/21 实测 941↔918、935↔834）——两个数不要混着报，以脚本为准，否则同一句「900字左右」两条稿会对不上 |
| 标题 | **一律 ≤20字（news/story 同限，无例外）**：写完即跑 `--check-title "<标题>" 20`，超限就地改短再入库 |
| 改法 | 编辑性修剪：保留开场金句、核心反差、引语、数字、支线。砍冗余修饰、重复的致歉/说明句、次要配角的发言。**结尾不做概括性收束**——删掉对称总结句，收在最后一条具体事实上（9/21 删掉「一边放弃舞台，一边搬进直播间」） |
| 强制闭环 | 假名计数 → renwei → `sqlite3 UPDATE` 重入库 → 密度 → 重评 → `score_dims` 覆盖落盘。**重入库必须先 `SELECT related_keys` 读出原值再原样回写**，否则关联被静默清空（PUT/UPDATE 全量覆盖语义） |
| 顺手补漏 | 改稿时检查该 key 的 `related_keys` 是否为空。空则补挂同企划/同人物历史 key（9/21 实测 `58925bff2975` 入库时漏挂，改稿时补上 3 条 Cloud ten 同企划 key：主题稿 + 已发出道稿 + 企划背景稿） |

命令级流程（含 `--check-title` 实测值、逐行字数定位、闭环验证脚本）见 `references/rewrite-to-target-wordcount.md`。

**"改到XX字" = 编辑性压缩，不是重写（7/1花田蓝衣教训）：** 当用户说"把A版本改到900字"时，意思是保留A版本的结构、叙事线、风格，在900字内做编辑性修剪。**不是**让你以素材为核心重写一篇不同风格的新稿。具体做法：
- 保留原版本的开头画面、引语、时间线骨架
- 压缩冗余描述、次要细节、过渡句
- 保持叙事驱动——如果改完后风格从"报道"变成了"评论"，说明你重写了而不是压缩了
- 自检："这篇和原版的区别只是字数吗？"如果连表达方式都变了，立即回退到压缩模式

## 结构要求（长文story必检项）

长文story（即DB中 `format='story'` 且 `is_long_form=1` 的素材）必须有清晰的##小标题分段，不能是一团连续文字。

- **写draft时就必须写入##小标题**，不是写完后补。第一次写稿时就把分段逻辑想好，每段写前先确定小标题，再写正文

### 覆盖重写时也必须检查小标题（6/29教训）

**当对已入库稿件进行覆盖重写时（包括只加小标题的修改），也必须走完整的阶段4→5闭环：PUT入库→密度检查→renwei→review。** 不能因为"内容改动小"就跳过review。

**即使renwei通过了、入库了，也必须在入库后立即跑5维度review评分（7/1教训：花田蓝衣）。** renwei确认"无AI味" ≠ 稿件质量达标。5维度review（爆发点、情绪价值、信息增量、内容深度、标题质量）是独立于renwei的强制步骤，不可跳过。

具体场景：
- 用户说"缺少小标题"→ 修改rewritten_content后，必须重新走review（密度+renwei+5维度）
- 用户说"再改一下"→ 改完必须重跑review确认
- 即使只是调整段落结构、加/改小标题、删减内容，也必须重新过review

**跳过review的后果：** 6/29 session中，第一次对佐野丽奈稿件做覆盖重写（只加小标题）后，直接PUT入库就汇报完成了。用户查看后指出缺小标题——原因是review（5维度）环节中"长文结构要求"本来就会检查##标题，如果走了review循环就能在汇报前发现问题。

**自检方法（PUT之前）：**

确认1：正文中是否包含 `##` 开头的行？
确认2：每个 `##` 小标题下方是否有至少一段内容？
确认3：小标题数量是否与逻辑段落数匹配（至少2-4个，取决于文章长度）？
确认4：是否有用 `**加粗**` 冒充小标题的情况？

## Renwei审读实操速查（6/28经验）

### ❌ `##` 小标题 vs `**` 加粗的常见混淆（6/29纠正）

**关键事实：** Renwei 脚本的「加粗滥用」检测只匹配 `**文字**`（标准Markdown加粗语法），`## 标题` **完全不会被命中**。6/29 session中触发加粗滥用的原因是我用了 `**二宫和也：走向全球的"不确定性"**` 这种写法（误用加粗语法代替标题语法），而不是用了 `## 二宫和也：走向全球的"不确定性"`。

**正确做法：**
- 长文story的小标题必须用 `## 小标题` 语法
- 绝对禁止用 `**小标题**` 代替——这会被renwei标记为「加粗滥用」
- 如果renwei拒绝的原因包含「加粗滥用」，检查draft里是否有 `**` 加粗段落，全部替换为 `## 标题`
- Pitfall：我在6/29 session三篇稿件全部因用了 `**加粗**` 写小标题被renwei拒绝。改为 `## 标题` 后全部通过。

### ⭐ 顿号预检前移到写稿之后、renwei 之前（9/20 实测：31 篇 exit1=0）

**最省轮次的一步：全部 draft 写完后先跑一条「行内顿号≥2」扫描，改净再进 renwei。** 9/20 批 31 篇（含 8 story + 13 news + 6 gzh）只命中 9 行，全部在 renwei 之前改掉，renwei **exit 1 = 0**（exit 2 仅 3 篇，均为单处非聚集：格言公式 ×2、签到式过渡 ×1）。对比 9/13（29 篇 exit1×5）、9/17（36 篇 exit1×1 + exit2×12），把「renwei 报行号 → 按预览猜 → 重跑仍报同一段」的 2–3 轮压到 0 轮。

```python
for f in sorted(glob.glob('/tmp/drafts/*_draft_*.md')):
    for i, l in enumerate(open(f).read().split('\n'), 1):
        if l.count('、') >= 2: print(f, f'L{i}', '|', l)   # 打印整行，不截断
```

**硬约束（写稿时就落笔，不靠事后修）：** ①≥3 项真实人名/物品/曲名枚举一律用间隔号 `·`（U+00B7）；②句子里 ≥2 个「，」或「、」时，收尾不要用「的/是/和」（9/13 第二形态）；③小标题行不放 ≥3 项枚举；④禁止自写「逗号也计数」的模拟正则——renwei 真条件是 `re.search(r'([^，。！？]{2,8}[，、]){2,}[^，。！？]{2,8}(的|是|和)')` **AND** `'、' in line` **AND** `line.count('、')>=2`，只用顿号数量做预检即可（自写模拟会误报 20+ 行普通句子）。

**同日「迟到的行」复核（9/20 新增）：** 收尾验证时必须重查一次 `date(created_at)=当天` 的条数——9/20 启动 dump 是 55 行、收尾变成 56 行（`c4e51b360af2` 是批中新入库的同事件素材）。**新增行不要当漏写补第二篇，按同事件挂到主稿的 `related_keys`。**

### 頓号（、）枚举误判为排比三连（7/5经验 + 7/28补充）

Renwei的「排比三连(顿号分列)」检测不仅匹配真正的排比句式，也会命中**普通的中文顿号列举**——人名列表（「二宫和也、樱井翔、松本润」）、并列名词（「日常、爱好的、手工作品」）、列举式描述（「发日常、发兴趣、和粉丝共享空间」）。这些不是排比，是中文正常的枚举写法。

**判断方法：**
1. 检查命中文字是否只是普通话的顿号列表（人名、物品、概念列举）
2. 如果是真实的人名/物品枚举 → 换用「和/与/以及」连接，或加括号写成「二宫和也等」，或在`、`之间补充连词减少列举感
3. 如果是「发日常、发兴趣、和粉丝共享空间」这类动词+名词的列举结构 → 改写成「那里放他的日常和兴趣，和粉丝共享」等非列举句式
4. **不要为了过检测而删除有效信息**——人名列表是正常中文，只需要轻微调整即可让renwei接受

**7/5验证：** 大野智稿三次exit 1均因顿号分列。前两次改「句式」本身没用（因为renwei匹配的是`、`符号本身），第三次改成括号+和/与才通过。

**7/28补充：单顿号（两项枚举）被误判为排比三连—极端场景处理**
当 renwei 将 `活动十周年、二十五岁` 这种仅含 **一个顿号的两项枚举** 也标记为「排比三连(顿号分列)」时，这属于正则的过度匹配（脚本匹配了 `、` 的存在而非要求3个以上）。处理方式：
- 对 **1个顿号**（两项枚举）：直接改 `、` 为「和/又/并+连词」即可，不需要重构句子
- 对 **2个以上顿号**（三项枚举如「好的坏的、光鲜与灰暗的、自信与笨拙的」）：不要逐个替换顿号为 `和/与`——这样产生的中文（「好的坏的和光鲜与灰暗的时刻与自信与笨拙的表现」）很生硬。**最佳修复：完全改写句子，消除枚举结构**。改为「所有一切都还原在书中」或「她把经历的一切都写进了书里」等非枚举句式。一次到位，不反复调整顿号位置。

**8/6补充：真实人名列表的间隔号·修复（验证一次通过）** — 当顿号命中是**真实人名/成员名单枚举**（如「富田菜菜风、樱井桃、铃木瞳美和蟹泽萌子」）时，只把最后一个顿号改成「和/与」仍可能残留2个顿号继续被拒（8/6实测：改「和」后renwei仍exit 1）。**最佳修复：把人名之间的顿号换成间隔号·**——「富田菜菜风·樱井桃·铃木瞳美和蟹泽萌子」→ renwei 0命中通过。间隔号·不在renwei「顿号分列」正则匹配范围内，且保持人名列表可读性，比重构句子损失的信息更少。适用于必须保留全部人名的场景（成员名单、出演阵容），8/6在豆田/≠ME稿三处人名列表全部用此法一次通过。

**8/24补充：书名号《》包裹的曲名连排即使换间隔号·仍可能命中「排比三连」** — 乃木坂live稿「夏曲连发：《逃水》·《太阳敲击》·《Offshore Girl》·《不道德之夏》」在顿号→·之后仍被标记（L11）。《》包裹的曲名列表是renwei正则的顽固命中点，间隔号·对它不完全有效。**对策：曲名连排改用叙述式展开**（如「《逃水》起头，一路唱到《不道德之夏》，中间还有《太阳敲击》《Offshore Girl》」）或只保留2个书名号+「等」收束，比硬换分隔符更可靠。

### Renwei exit code 2 处理规则

Renwei exit 2 = warning（非聚集信号），不是拒绝。具体对策：

| 命中模式 | 判断 | 处理 |
|---------|------|------|
| 单一类信号、非聚集（≤3处散布在不同段落） | ✅ 接受，通过 | 不改 |
| 单一类信号、同段落2处以上（如连续两句有破折号） | ⚠️ 建议修 | 只改聚集段落，不改全文 |
| 多类信号混合但每类≤2处、散布 | ✅ 接受 | 不改 |
| exit 1（拒绝） | ❌ 必须改 | 按 `references/6-27-renwei-rejection-recovery.md` 修复 |

**6/28验证：** 本session跑了~15次renwei，全部exit 2，全部接受（最终稿用户无投诉）。
常见exit 2模式：破折号1-3处（不同段落）+ 偶尔单处排比/格言。这些都是非聚集，直接通过。

### 破折号批量替换技巧（7/1经验）

renwei对破折号（`——`）高度敏感。当一篇draft有10+处破折号导致exit 1时，逐处patch效率极低。用sed批量替换：

**8/21补充：`##`小标题行和作品名内的破折号同样被renwei计入「格式痕迹」。** 小标题「『脱离欅坂才笑得出来』——那其实是歌曲里的笑容」命中后改`——`为`：`；作品名《夜曲——在这怪诞之夜》命中后改`——`为间隔号·（《夜曲·在这怪诞之夜》）。修完重跑renwei确认。

```bash
# 批量把中文破折号替换为句号（断开长句）
sed -i 's/——/。/g' /tmp/xhs_draft_xxx.md

# 或替换为冒号（解释关系）
sed -i 's/——/：/g' /tmp/xhs_draft_xxx.md

# 或替换为逗号（平铺关系）
sed -i 's/——/，/g' /tmp/xhs_draft_xxx.md
```

然后检查替换后上下文流畅度，调整个别位置。先把破折号降至≤3处，再处理残留的格言/排比。破折号降下来后，exit 1通常变为exit 2。

**8/18补充：python split-join「保前N法」比sed更精细（深访稿适用）** — 深访稿破折号常达13+处（8/18基拉·梅、Cloud ten各13处），sed全删会伤引语语气。用split保留前2-3处、其余替换为逗号：`parts = c.split('——'); out = parts[0]; out += ''.join(('——' if i <= N else '，') + parts[i] for i in range(1, len(parts)))`（N=2或3）。一次命令13→2，再跑renwei验证。若替换后句意变碎，把个别逗号改冒号（解释关系）。

**8/18补充：深访稿破折号聚集用「保留前N处」python批量法** — 长深访稿（基拉·梅3709字、Cloud ten 2532字）写完后破折号各13处 → exit 1。逐处patch太慢，sed全局替换又太粗暴（会把引语内有修辞价值的"不是A——而是B"转折也抹掉）。用split保留前2-3处、其余替换为逗号：
```python
# 保留前maxkeep个破折号，其余替换为逗号
parts = c.split('——')
out = parts[0]
for i in range(1, len(parts)):
    out += ('——' + parts[i]) if i <= maxkeep else ('，' + parts[i])
```
降级后重跑假名+renwei。**写深访稿（目标≥2000字）时破折号天然会累积，落笔时就控制每篇≤3处，不要等renwei反馈才处理——8/18实测两篇深访都因13处破折号白跑一轮renwei。**

**9/7补充：破折号4-6处但exit=2（非聚集散布）的稿也建议降到≤3处再入库** — 批量写稿时短news/story初稿普遍带4-6处破折号，renwei判exit=2（"非聚集散布可接受"）不拦，但同一类信号4-6处散布在review阶段观感差、且后续任何patch都可能再引入聚集。9/7实测S3(4处)/A3(5处)/A1(6处)/S4(3处)用"保护引语内破折号+保留前N"的python一次降量到≤3处，全部renwei exit 0/2通过。**引语内（「」内）的破折号是被采访者原话，不要降**——用占位符保护再split：
```python
import re
def reduce_dash(fn, keep=2):
    c = open(fn).read()
    n = c.count('——')
    if n <= keep: return
    protected = {}
    def prot(m):
        idx = len(protected)
        protected[idx] = m.group(0)
        return f'§PROT{idx}§'
    # 1) 保护「」内的破折号（被采访者原话，不降）
    c2 = re.sub(r'「[^」]*——[^」]*」', prot, c)
    # 2) 只对引语外的破折号做保留前N
    parts = c2.split('——')
    out = parts[0]
    for i in range(1, len(parts)):
        out += ('——' + parts[i]) if i <= keep else ('，' + parts[i])
    # 3) 还原引语
    for idx, orig in protected.items():
        out = out.replace(f'§PROT{idx}§', orig)
    open(fn, 'w').write(out)
    print(f'{fn}: dash {n}->{out.count("——")}')
```
**9/7实测：** 16篇draft中S3/A3/A1/S4共4篇（4-6处）用此法降到2-3处，S5的5处因全部在叙述句（无引语内命中）直接全量替换为逗号→0处exit 0；全部重跑renwei通过。降量后必须重读文件确认替换处语义通顺（逗号断句是否自然），不能只看exit码。

**注意：** 引语内的破折号（被采访者原话中的`——`）不需要改写。在用sed做全局替换前，先确认draft中哪些破折号在引号内——可以暂时用占位符保护（如将引语内`——`换为`←→`，批量替换全局后再改回）。但实践中引语内破折号通常只有1-2处，全局替换后手动补回更快。

### 列表/要点式内容的renwei false positive（7/3经验）

当 renwei 拒绝原因是「短句轰炸」且命中位置是**列表/要点式排版**（如人物名单、活动日程、并列条目）时，这是因为 renwei 的短句检测是按行独立匹配的，不区分排版结构。

**判断方法：**
1. 检查命中行是否属于「项目列表」（`- xxx`）、「枚举式段落」（`xxx、yyy、zzz`断行）、「JSON/列表排版」
2. 如果是列表结构 → 合并为叙述性的一句话即可修复
3. 如果是内容本身需要枚举（如「A包括X、Y、Z三人」）→ 直接连成一句用逗号分隔

**秋元康客座教授稿案例（7/3）：** 5位教授名单分布在5个`-`列表项 → renwei判定为5处短句轰炸exit 1。修复：合并为一句「包括A、B、C、D和E」→ exit 0通过。这不是写作质量问题，是列表排版和renwei正则匹配的冲突。

**8/2补充：数字编号歌单同样触发「短句轰炸」** — ≠ME稿的歌单（`1.请爱我吧 2.在这里初吻 … 8.≠ME` 8行编号列表）全部命中短句轰炸，加歌单标题段也无法豁免。修复：改为叙述性单句「歌单从《请爱我吧》开场，经《在这里初吻》《偶然交响曲》《喝彩游行》……到同名曲《≠ME》收尾，8首歌一气呵成」→ exit 0。**另见歌名拆字陷阱**：把歌名拆成单字加顿号（「请、爱、我、吧」）会命中「排比三连(顿号分列)」，改写为「歌名拆字的挑战」式表述即可，不要保留顿号分隔。

### 引语内renwei false positive（7/1经验 + 7/15补充：第一人称SNS素材）

renwei 的「不是X而是Y」「排比三连」「破折号」检测**是逐字符正则匹配，不区分AI生成文字和直接引语**。当命中位置全部落在被采访者的原话引号内时（如「播音员也不是，模特也不是，演员也不是——那我是什么屋さん呢？」——这是田中皆实的原话），这些命中不代表AI味，而是**被采访者的原始发言被renwei误判**。

**7/15补充：第一人称SNS/争议素材的renwei天然高拒率**
当素材是当事人在SNS（X/Ins）上发布的第一人称内容，改写稿大量引用原话时，renwei接近必然拒绝。原因：当事人原文中的表达（「每个人都有自己的路要走」「反对也好、劝说也好、倾听也好」）本身就是「格言式」「排比式」的——renwei会判定为改写者的AI味，但它其实是当事人的原话风格。

**8/5补充：「不是X就是Y」在引语内也被命中「不是X而是Y」** — 转述成员间玩笑「袋里不是饭团就是蛋白质食品」命中「不是X而是Y」句式（实际是「不是…就是…」二选一结构，非「不是A而是B」转折）。即使命中位置在被采访者原话引号内，只要与其他信号聚集成exit 1，就需要改写：把「不是X就是Y」换成「要么X要么Y」（「袋里要么饭团要么蛋白质食品」）即可干净通过。这类二选一结构在口语转述中高频出现，写稿时直接预判用「要么…要么…」。

**8/9补充：「既不是X也不是Y」双重否定同样命中「不是X而是Y」** — 菊池风磨稿「既不是太难也不是太简单」被标记为「不是X而是Y」。修复：改写为正面表述「难度拿捏得很妙」（或「不太难也不太简单」但避免"不是"字样）。写稿时涉及"难度/状态适中"类表述，直接预判用「拿捏得刚刚好」「卡得正好」等正面句式。

**9/26补充：记者转述句里的「并不是…，而是…」/「不是…就是…」同样命中（非引语）。** 三批 41 篇实测 2 例：800a6d566429「她说宵并不是自己意识到自己是王子，而是被周围这么叫」、d03e425fc670「不是因为穿了蓝色皮夹克就是小峠」。这类是**叙述句**而非当事人原话，不能按引语豁免处理。改法：一律改成正面表述——「本人并没有把自己当成王子，是周围这么叫出来的」「穿蓝色皮夹克不等于小峠」。落笔时预判：凡是要写「否定 A + 肯定 B」的对比，直接用「A 不成立，B 才对」以外的句式，或写成两个独立句。

**8/18补充：「不是X也不是Y，是Z」三连结构同样命中** — KEY TO LIT猪狩苍弥引语「给我打开这扇门权利的，不是佛祖也不是神明，是你们」被标记（引语内命中，但与其他信号聚集致exit 1）。修复：改成肯定式「给我打开这扇门权利的，是你们每一个人」。「不是X也不是Y，是Z」是当事人情绪化发言的高频结构，写稿时直接预判改写为肯定句，不要等renwei反馈。

**⚠️ 间隔号·会被假名计数器计入（8/9实测）** — renwei的顿号分列修复用间隔号·（如「富田菜菜风·樱井桃·铃木瞳美」）时，间隔号·本身是片假名区间字符（U+30FB），会被日文假名计数脚本计入。8/9「母・千代」计为1个假名。**用间隔号修顿号分列后必须重新跑假名计数**，如果间隔号导致假名超标（>5），改用「和/与」连接或中文顿号替代方案。

**8/11补充：区分两种间隔号——中文间隔号·（U+00B7）与片假名中点・（U+30FB）。** 修复顿号分列时**优先用中文间隔号·（U+00B7）**：它既不在renwei「顿号分列」正则匹配范围，也不在假名计数器区间（\u3040-\u30ff）内，一次替换同时过renwei+假名双门禁（8/11实测：山田胜己·长野诚·日置将士·秋山和彦·森本裕介、樽美酒研二·塚田僚一·菅田琳宁、巨济市·成员家乡庆州市·水原市、穿搭·妆容·音乐，替换后假名计数=0，renwei通过）。片假名中点・（U+30FB）才会被计入假名——8/9的教训针对的是误用U+30FB的情况。

**⚠️ 批量循环捕获退出码的管道陷阱（9/3实测）** — 批量跑多篇 renwei 时，`for f in draft_*.md; do r=$(ALL_PROXY="" python3 ... 2>&1 | tail -3); ec=$?; done` 里的 `$?` 拿到的是 **tail 的退出码**（恒为0），不是 python 的——整批误显示全部 exit=0，掩盖了真实的 exit=1 拒绝。**正确写法：重定向到文件再捕获，或用临时变量直接接 python 退出码：**
```bash
for f in draft_*.md; do
  ALL_PROXY="" python3 ~/.hermes/skills/writing/renwei-writing/scripts/renwei-pre-commit.py "$f" > /tmp/renwei_out.txt 2>&1
  ec=$?
  echo "$ec $f"
done
```
exit=2 是 warning（非聚集可接受），exit=1 必须修复，exit=0 通过。

**批量跑renwei的退出码捕获坑（9/3实测）：** `cmd 2>&1 | tail -3; echo $?` 里 `$?` 拿到的是 `tail` 的退出码不是renwei的——整批全部显示exit=0，实际有一篇exit=1被吞。**必须用临时文件重定向再取码：**
```bash

ec=$?

```
或一次性循环输出：`for f in draft_*.md; do ALL_PROXY="" python3 .../renwei-pre-commit.py "$f" > /tmp/rw_out.txt 2>&1; echo "$? $f"; done`。exit=1的再单独看/tmp/rw_out.txt定位命中行。exit=2（warning非聚集）可直接接受。

## 无声失败速查

| 错误 | API返回 | 实际结果 |
|------|---------|---------|
| 截短key（非40位SHA1） | `{"ok":true}` | 不落盘 |
| 不存在的字段名（如ref_keys） | `{"ok":true}` | 0条更新 |

## 密度计算完整规则（含关联素材）

**8/15批量密度检查双门禁+合并稿口径（53篇实作）：** 批量密度检查必须同时跑两个门槛，缺一不可：
1. **story lf=1 字数门禁**：`xhs_word_count.py` 算正文 <800字 = 不合格（即使密度≥30%）。8/15实测13篇story卡在532-799字，全部需要扩充。
2. **密度门禁**：≥30%。
**合并稿（同源重复/视角分工）的密度判定用「主素材密度」而非「合并去重后分母」**——body_xhs / 主素材content_ja 单算。8/15实测：霜月露娜合并稿按「主素材+关联去重」分母算18.7%看似不达标，按主素材密度27.8%仍差一点才需要扩充；熊田曜子按合并分母28.6%看似不达标，按主素材密度46.9%直接合格，省掉一次无谓扩充。**判断规则：先看该稿是独立成篇还是合并稿（related_keys非空且内容重叠），合并稿一律用主素材content_ja做分母。**

**8/17补充：续篇/时间线关联的旧文key不参与密度分母。** 山本舞香辞演稿关联8/15山崎天旧文（时间线补充，非同批同源重复），合并去重分母=19.8%假LOW，按主素材密度41.5%达标。**判定扩展：related_keys指向的是历史旧文/续篇素材（非本批同源重复）时，密度分母只用主素材content_ja，旧文只用于信息关联不进入密度基准。** 同理8/16的冈田将生关联570d5e67、阿部关联昨日c5f9b0a6、铃木关联昨日0646e08f、拉乌尔关联昨日森保一2条——全部按主素材密度判定。

**⚠️ 8/16补充：related_keys≠合并稿密度基准——只有「内容重叠/同源/同事件多角度」才合并分母（8/16批量27篇实测：5篇LOW中4篇误报）** — 批量密度脚本用「主素材+全部related_keys合并去重」做分母时，以下两类关联会把分母撑虚、误报LOW：
1. **时间线补充关联**（related指向昨日/历史旧文，如A8拉乌尔←昨日森保一2条、S3阿部←昨日FP旧文）：旧文是背景不是本稿内容源，合并后27.7%误报LOW，主素材密度41.9%实际达标。
2. **人物同框/社交圈关联**（related指向同框出镜者，如K10高桥由伸←K4能条爱未：两人在同一张照片里但稿件内容完全不同）：合并后18.6%误报LOW，主素材密度71.5%实际达标。
**操作流程：** 批量密度检查出现LOW时，先按此规则复核主素材密度（body_xhs / 主素材content_ja），只有「同源重复合并（内容几乎一样选最全key）」「视角分工（团体主稿vs人物侧写）」和真正合并进正文的同事件素材才用合并分母。复核后仍<30%才是真LOW，才需要扩充（8/16唯一真LOW是A9道枝CM采访22.9%，扩充2段后37.4%）。

```python
import sys, urllib.request, json, re
sys.path.insert(0, 'scripts')
from xhs_word_count import xhs_content_len

# 收集：主素材 + 每个related_keys素材的content_ja
keys = ['主素材key'] + ['关联key1', '关联key2']
all_text = ''
for k in keys:
    d = json.loads(urllib.request.urlopen(f'http://127.0.0.1:5000/api/news/{k}').read())
    all_text += (d.get('content_ja','') or d.get('content','')) + '\n'

# 去重：按 。！？拆句子，set()去重
sents = [s.strip() for s in re.split(r'[。！？]', all_text) if s.strip()]
dedup = list(dict.fromkeys(sents))
dedup_xhs = xhs_content_len('。'.join(dedup))

body_xhs = xhs_content_len(正文)
density = body_xhs / dedup_xhs * 100  # 密度≥30%才通过
```

## 标记纪律

入库时同时设置：
- `preselected: 1`（预选标记，必设）
- `publish_xhs: 0`（写稿阶段只预选，不发。需发布时人工或pipeline单独设）
- **`publish_method`（字数路由，必设，2026-10-05起）**：
  - `content_ja > 3000` 字的 story → **`'export'`（长文模式，字数不限，正文按 原文×0.31~0.33）**
  - 其余 story → **`'post'`（图文，正文 900±50，硬上限950）**
  - news → `'post'`（≤900）
  - 判据：900字×30%密度 = 原文3000字阈值；人物弧跨年稿（偶像生涯史/家族口述/争议深度）即使原文略低也优先 export。**长文无数量配额，够格就走 export。** 详见 `references/longform-vs-900-routing.md`。
  - ⚠️ 写正文前就要定路由——**长文稿不要压到900字**（压了等于把邮件塞进信封再扔掉一半）。

### 跨日重复条 / 同事件合并条的统一标记（9/24-9/26 三批新增）

跨日批次里「同一事件在 A 日被判 S 级、在 B 日被判 C 级重复」的情形，用一条统一约定处理，避免次日跨日覆盖检查把它当漏写：

| 形态 | 落库写法 |
|------|---------|
| 成篇主条 | `rewritten_title/rewritten_content` + `publish_mode='rewritten'` + `preselected=1` + `publish_xhs=0` + `related_keys`（含被吸收条与其他被覆盖条的全 40 位 key） |
| 同事件重复条 / 被吸收条（AKB 大 TOP 或 S/A 级） | `preselected=1` + `publish_xhs=0` + `score_dims='merged-into-<主条key12>'` |
| 被 related_keys 吸收但不算 AKB 大 TOP 的备选条 | 保持 `preselected=0`（预期状态，不处理） |

判据：`score_dims` 以 `merged-into-` 开头 = 已决策覆盖，**不是漏写**。9/24-9/26 实作：青叶坂研讨会 8 条 + 桃乃木 3 条 + STARTO 跨年 2 条 + 高比良/大野爱实 + 9/25 井上和 5 条，共 28 条按此标记。

### 续集/续篇素材的处理规则（7/1教训）

当素材是同一事件的**后续**（同人物/同事件已有前篇已入库 `rewritten_content`）时：

**核心原则：续集 ≠ 独立报道。** 续集不重复前篇已经覆盖的事件经过和画面描写。假设读者已读过前篇。

**写法对比：**

| 前篇写过的 | 续集应该写 |
|-----------|-----------|
| 事件经过（谁、何时、发生什么） | 新进展/新观点/新角度 |
| 当事人原话引语 | 第三方分析、观察者评论 |
| 现场画面描写 | 深度分析、传播机制 |
| 基础信息（人物背景） | 规律总结、行业洞察 |

**自检清单：**
1. 开头是否在重复前篇的基本事件？如果是，砍到一句话以内快速过渡
2. 本文的核心信息点中，有几个是前篇完全没有提到的新角度？（至少1个）
3. 读者读前篇后再读这篇，能获得的增量信息是什么？

**关于翻译版（DB的`content`字段）的review规则：**
- 翻译版不做信息增量评分（满分8分，不计标题/信息增量）
- 翻译版5维度通常5-6分 = 合格的资料参考
- 翻译版**不能**作为可发布稿件的改写版评分
- 改写版（`rewritten_content`）正常满分10分评分

详细参考 `references/7-1-sequel-writing-vs-independent-report.md`。

## write-api.py 使用陷阱（7/16经验）

### 陷阱1：draft文件第一行必须是 `## 标题` 格式

write-api.py 的核心逻辑是 `lines[0]` 提取为标题（strip_md_title去`#`），`lines[1:]` 为正文。

**❌ 常见错误写法（7/16集体踩坑）：** draft文件第一行没有 `#` 或 `##` 前缀，直接写正文第一句。脚本会把正文的第一句当作标题写入rewritten_title，剩下的正文只剩极短片段。

**✅ 正确写法：** 每篇draft第一行必须是 `## 实际标题`：
```markdown
## 高桥南晒蔬菜满桌，粉丝：全部美味分量

正文内容从这里开始...
```

### 陷阱2：draft中写了 `# S-1 标题` 格式（编号前缀残留）

strip_md_title 会去掉 `#` 但不会去掉 `S-1 ` 前缀。如果写成：
```markdown
# S-1 前田敦子35岁生日
```
入库后 rewritten_title = `S-1 前田敦子35岁生日`（前缀残留）。

**✅ 正确做法：** draft第一行直接用 `## 干净标题`，不要加编号前缀。入库后再修正标题非常麻烦（需要单独PUT覆盖）。

### 短news的替代入库方式

对于短news（`format=news` 或 `is_long_form=0`），直接用 Python urllib PUT 比 write-api.py 更安全高效：

```python
import urllib.request, json
payload = json.dumps({
    'rewritten_title': '标题',
    'rewritten_content': '正文...',
    'publish_mode': 'rewritten',
    'preselected': 1,
    'publish_xhs': 0,
}).encode('utf-8')
req = urllib.request.Request(f'http://127.0.0.1:5000/api/news/{key}', 
                              data=payload,
                              headers={'Content-Type': 'application/json'},
                              method='PUT')
urllib.request.urlopen(req, timeout=10)
```

优点：完全控制标题和正文，不给write-api.py的自动解析留风险空间。

### 第一人称自述素材的renwei误判（2026-07-15经验）
当素材来自当事人在SNS上的**第一人称发言**（X帖子、Ins caption等），改写稿中大量引用其原话时，renwei容易将当事人原文中的「格言式表达」误判为改写者AI味。
详见 `references/first-person-testimony-renwei-fp.md`。
关键判断：所有命中位置是否全部在引号（「」）内。如是→renwei对当事人原文风格的误判。

### 争议型/受访者观点素材处理（7/6教训）

当素材内容是**受访者发表的争议性观点**（如约会谁付钱、恋爱观等容易引发网络争议的发言）时：

**❌ 错误处理：** 因为"话题争议"就跳过不写。争议本身不是不让写的理由。

**✅ 正确做法：**
1. **不站队，当观察者** — 把多方观点摆出来（原文批判方 + 支持方 + 其他艺人不同年龄段的不同看法），读者自己判断
2. **合并多篇同事件报道** — 同一事件可能有多角度的报道（一篇偏网友反应、一篇补充上下文、一篇有搞笑艺人后续调侃）。全部通读后合并，信息面更广
3. **写法：中立叙述+三方观点** — 起因（谁说了什么）→ 反应（争议各方观点）→ 延伸（其他艺人/搞笑艺人添油加醋）。不做价值判断，让数据/引语说话
4. **related_keys** — 同事件的每篇素材都需要互设related_keys，方便后续查关联

**判定标准：** 判断"能不能写"的关键不是"这个观点对不对"，而是"读者对这件事有没有讨论的欲望"。争议型素材在小红书天然有流量，关键在于怎么写——不是教读者该怎么想，而是呈现事件让读者自己站队。

**实战案例（7/6）：** 大岛麻衣"约会女性别掏钱包"发言→3篇同事件报道合并（大岛发言原文+网友/中嶋优月/杉本彩反应+真栄田贤指名制调侃），写入同一个rewritten_content，互设related_keys。密度26.4%走多观点综合报道豁免。

## 同事件多素材合并为xhs短稿（7/6新增模式）

前面的「多篇xhs素材合并为公众号专题稿」处理的是合并为**公众号长文**的场景。同样重要的是合并为**xhs短篇**的场景：

当同一事件有**2-3篇短素材**（如：当事人发言+网友反应报道+搞笑艺人跟进调侃），且角度互补不重复时，可以**合并为1篇xhs稿**，而不是各自独立写3篇。

**适用条件：** 各素材围绕同一事件，角度互补不重复（一个说事、一个说反应、一个说后续）
**另见对立观点碰撞型合并：** `references/7-6-same-event-blanket-merge.md` → 「7/15案例：对立观点碰撞型合并」

### 同源重复合并（8/1新增子类：5-6条几乎相同内容的媒体重复报道）

当同一事件的多条素材是**同一消息源的重复报道**（标题略不同、正文高度重合，如多家媒体同时转发某电影主题曲官宣、某特番预告）时，合并标准与「多角度互补」不同：

| 维度 | 多角度互补（7/6） | 同源重复（8/1） |
|------|------------------|----------------|
| 素材关系 | 各写各的角度（发言/反应/后续） | 内容几乎一样，只是措辞不同 |
| 选key | 写最完整/最新的key | **选 content_ja 最长的key**（信息最全） |
| 正文 | 按时间线编排各角度 | 从最长素材提炼全部事实点，其余素材只补遗漏细节 |
| related_keys | 必须互设 | 全部关联素材互设（8/1：6条电影素材→1篇主稿+5条related） |
| 密度判定 | 多人物综合豁免 | **主素材密度判定**（正文xhs_len / 主素材content_ja，≥30%即过；合并基准虚大不适用） |

**8/1实作：** 西畑大吾×福本莉子电影《时薪300日元的死神》主题曲官宣6条同源→合并1篇（主素材2992字，正文967字，主素材密度32.3%通过）；向井康二×桥本直关西特番预告5条同源→合并1篇（主素材2328字，正文900字，主素材密度38.7%通过）。合并密度9.8%/12.3%看着吓人，但那是6/5条累加的假分母——用主素材密度说话。

**操作：** 写稿前如果 `search=` 命中同一标题事件的≥3条素材且读完发现内容高度重合，先确认是同源重复而非多角度；同源重复直接选最长key当主素材，一次性通读主素材全文（关联素材不必逐字通读，scan确认无遗漏事实点即可），写1篇。

### 视角分工稿密度判定（8/3新增：同一事件两篇不同视角互设related_keys）

当 review 对同一事件簇明确分工为「团体主稿 + 人物侧写」（如乃木坂TIF团体视角 A1 + 井上和主席视角 A2），两篇互设 related_keys 后，合并基准密度会虚低（8/3实测 A1=23.7%、A2=23.6%），但这是**视角分工而非内容重复**——两篇正文各自覆盖不同信息面，不该被合并基准误伤。

**判定：** 视角分工稿密度按「主素材密度」判定（body_xhs / 主素材content_ja，≥30% 即过）。8/3验证：A1=43.8%、A2=51.4% 均达标。

**与同源重复合并的区别：**

| 场景 | 选key | 密度基准 |
|------|-------|---------|
| 同源重复合并（8/1） | 选 content_ja 最长的1条当主素材，其余只做related | 主素材密度 |
| 视角分工稿（8/3） | 两篇各自独立成稿，各自用自己的key当主素材，仅互设related_keys | 各自主素材密度 |

先分清场景再算密度：同源重复=内容几乎一样选最全的；视角分工=review明确标注"团体主稿vs人物侧写"分工的，两篇都要写。

**流程：**
1. 通读所有相关素材的content_ja全文
2. 找出信息交叉点（不要重复写同一个引语）
3. 按时间线或逻辑顺序排列（起因→反应→延伸）
4. 写入最完整/最新的那个key的rewritten_content
5. 所有关联key互设related_keys（双向关联）

**密度处理：** 多素材合并后原文基数增大，密度可能低于30%。按多人物多角度看，走综合报道豁免路径——只要信息增量充足（合并带来了各素材独有的内容），即使<30%也可以入库。

**关键差异 vs 公众号合并：**
| 维度 | xhs短稿合并 | 公众号长文合并 |
|------|------------|--------------|
| 字数 | 500-800字 | 1500-2000字 |
| 结构 | 时间线/逻辑顺叙 | 人物线/主题线交替 |
| 写入字段 | rewritten_ 字段 | wechat_ 字段 |
| related_keys | 必须互设 | 可设可不设 |

### ❌ query.sh --search 搜不到已有素材（7/9经验）

当 `bash query.sh --search "关键词"` 返回空结果，但review分级中有该素材（ts≥4.5）时，**不要假设素材不存在**。search接口可能因中文/日文混合文本索引问题漏掉有效素材。

**正确做法：** 用全量list dump还原完整key列表，然后从rows的title字段搜索：
```bash
bash ~/.hermes/workspace/query.sh --date_from <DATE> --limit 200 --sort_by title_score --sort_dir DESC > /tmp/full_list.json
python3 -c "
import json
with open('/tmp/full_list.json') as f:
    d = json.load(f)
for r in d['rows']:
    if '关键词' in r.get('title',''):
        print(f\"key={r['key']} | cj={len(r.get('content_ja','') or '')}字\")
"
```

详见 `references/search-endpoint-blind-spot.md`。



### 同人物/同事件多素材聚合 → 公众号/长稿（7/5经验）

当 review 发现同人物有大量素材（如龟梨和也·田中皆实共11条），且用户要求整合为公众号长文时，走以下流程：

### 1. 定位全量素材

用 API search= 搜索同一人物/事件关键词，找到所有相关记录。

列出每条的 title、rewritten_title、content_ja长度、created_at。注意同人物可能有多个拼写/别名。

### 2. 按素材类型筛选

- **公告类**（官宣、时间线）：提供背景事实，不需全文细读
- **深访类**（长文≥1500字）：**必读全文**——含人物自述、引语、背景，是核心素材
- **行业分析类**（现象评论）：提供第三视角，用于行业段
- **同事件重复**：跳过，只保留1条最丰富的

### 3. 找跨素材共同线索

通读长发素材时，关注：跨素材出现的同一句话/同一视角（可作为主题线索）；共同的成长弧线（劣等感→努力→突破）；时间线上的关键节点。

### 4. 公众号写作要点

- **开头：** 用最新素材+最有画面感的场景切入
- **中间：** 两条人物线交替叙述，找对照
- **行业段：** 简洁，作为注脚
- **结尾：** 回到开头场景，自然收束，不总结不升华

详见 `references/dual-channel-merge-pattern.md`——先读当前DB状态，合并payload一次PUT，不覆盖已入库的小红书版。
