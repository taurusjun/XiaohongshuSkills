# 跨日批次覆盖检查（8/1实作案例）

## 触发场景

用户说"开始写稿"后，主批次（当日S/A/AKB）写完，用户追问：
- 「7-31日的素材还没有写稿吧」→ 前一日批次从未写过
- 「改稿循环做了吗」→ 需要证明流程闭环

## 根因

写稿启动时只读了当日 daily review 存档（`~/.hermes/daily-reviews/2026-08-01.md`），
没有检查前一日（7/31）素材的 preselected 状态。7/31 的 review 文件存在（2026-07-31.md，
64条），但所有素材 preselected=0 —— 说明 review 跑了但写稿从未执行。

## 跨日检查操作（写稿启动时必做）

```bash
# 1. 前一日素材状态
curl -s --noproxy '*' 'http://127.0.0.1:5000/api/news?date_from=2026-07-31&date_to=2026-07-31&limit=200'
# 2. 当日素材状态
curl -s --noproxy '*' 'http://127.0.0.1:5000/api/news?date_from=2026-08-01&limit=200'
```

用 python 输出「已写（preselected=1）/未写（preselected=0）」对照。
未写清单里排除垃圾标题（含「我的标题/标题规则/生成的中文/重复了/引流摘要/- the final」等），
剩余就是待补范围。

## 8/1 实际数据

- review 文件：2026-08-01.md（01:43生成，覆盖34条）
- 但写稿启动时 API total=58 —— 02:00 档又入库24条新素材
  （西畑大吾死神×6、向井康二×5、Snow Man THE FIRST TAKE、黑木康正、高梨亚妖等）
- 这些 post-review 素材不在分级文件内，需要列出来与用户确认或按同事件聚类自行合并

## 补写批次要点

7/31 补写 10 篇（S级7 + AKB大TOP 3）时发现的额外注意：

1. **同事件合并**：伊藤百花主角卡（99a0d90f...story 1815字）+ 重复条（69ceb736...）
   + 津田贴纸条（05822991...）三个 key 是同一场 CM 发布会 → 合并写1篇，其余 key
   只设 related_keys。同类：高桥文哉蓝锁（S2）与 8/1 新素材对谈条（9ee8279d...）
   跨天同事件 → 新素材条并入 S2 作 related，不单独写。
2. **截短key查关联素材会404**：从 list 端点取到的短key直接 GET detail 返回
   HTTPError 404 —— 必须先用 list dump 找到完整40位key再读 content_ja。
3. **假名高频来源新增**（7/31批次）：艺人昵称（みちょぱ→MICHOPA）、综艺节目名
   （見取り図じゃん→见取图JUAN、ぐるぐるナインティナイン→转转NAINTY NINE）、
   产品谐音名（にふぉるめーしょん→二次元贴纸）、搞笑组合名（くだん→迪安，注意
   原词是ダイアン=Dian，曾误读为"天津饭"）。
4. **多素材合并密度**：S2 高桥文哉 21.8%、AKB1 伊藤百花 27.9% 都低于30%，
   但主素材密度分别为 62.8%（832/1324）和 46.4%（842/1815）——关联素材主要是
   名单/重复噪声，按「原文基数虚大」规则通过（参考 multi-material-merge-density-edge-case.md）。
5. **S7 影山优佳 29.9%** 差0.1% → 结尾补一句（从偶像转型演员的第10年……）过线，
   补完必须重跑 renwei（补句含破折号会新命中1处，exit 2非聚集可接受）→ 重入库 → 重review。

## 汇报格式

补写批次汇报时与主批次同结构：密度总览表（标 * 注明多素材合并/主素材密度）+
story 5维度评分表 + 关联处理说明 + 入库状态验证（sqlite3 content非空 10/10）。
同时明确剩余未处理素材（如 8/1 02点档24条）等待用户决策。
