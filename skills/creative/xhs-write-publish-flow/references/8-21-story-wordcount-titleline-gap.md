# Story字数门禁：本地draft计数含标题行，落库正文不含（8/21实测）

## 症状

5篇story（a6851683b242 / 31efb64af5e6 / c831dfdcd98f / 6540fdc4c96d / 8dbd796edf39）本地检查全文件字数均≥800：

| key | 本地全文件 | 落库DB复查 |
|-----|-----------|-----------|
| a6851683b242 | 809 | 775 SHORT |
| 31efb64af5e6 | 825 | 786 SHORT |
| c831dfdcd98f | 834 | 762 SHORT |
| 6540fdc4c96d | 822 | 789 SHORT |
| 8dbd796edf39 | 800 | 768 SHORT |

差值≈标题行长度（25-40字）。

## 根因

- draft第一行是 `## 标题`，入库逻辑 `lines[1:]` 把它剥离为 rewritten_title
- 本地 `xhs_word_count.py "$(cat draft.md)"` 统计的是全文件（**含**标题行）
- 标题行恰好把压线的800+拉回800以下，全部静默失败，直到入库后DB复查才暴露

## 对策

1. **本地字数检查按body-only**：`'\n'.join(lines[1:])` 传入 xhs_word_count.py，与落库口径一致
2. 或全文件计数目标**≥830字**（留出标题行余量）
3. **story字数门禁最终判定以落库后API GET的rewritten_content为准**——入库后必须复查，不能信本地数字
4. 扩充修复闭环：draft扩充 → 假名计数 → renwei → 重入库(sqlite3 UPDATE) → API GET复查字数

## 本次修复

5篇各扩充40-70字（从content_ja挖细节/引语），全部回到818-838字。

**扩充时的语义重复坑（连带验证）：** a6851683b242首轮补充句「这场演出被受灾地的观众记在心里，很多人告诉她『听了你们的歌…』」与下一段已有的「她说有观众告诉她『这首歌给了我鼓励』」是同一信息点，通读发现后改写为「纸飞机承载着把心愿送出去的意象」——扩充前重读draft全文，新增内容必须是不在已写信息点清单里的新信息（与8/18福田由爱案例同源，此处为批量扩充场景再次验证）。
