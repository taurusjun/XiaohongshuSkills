## 2. 规模上限与「按日闭环」纪律（本轮最重要的新增）

单日 30 篇左右的批次，一天一轮工具调用可以跑完；**四天 97 篇不可能在一个会话里做完**。做法：

- **按日闭环，一天一轮**，顺序 **最新 → 最旧**（10/1 → 9/30 → 9/29 → 9/28）
- 每一天内部走完整 A→B→C：写稿 → `batch_precheck.py` → renwei → 入库 → score_dims 落盘
- **当天没闭环完，不要开下一天**。已入库的部分是进度，留在 /tmp 的 draft 会随会话重置丢掉
- 用户连说「继续」时，就是接着下一天，不需要重新确认范围

## 3. 跨日去重要扫「已写的稿」，不能只扫当天 review 的聚类

**本轮实际踩到**：9/28 写了 `fa0f6a01`（111曲/团体视角），9/29 又写了 `d992d49589ad`（推席名次/佐藤绮星视角）——**同一场 9/26-27 K-Arena 演唱会写了两篇**，两篇都进库、都进了发布队列。

根因：每天各扫各的 review 聚类，没回头看前一批已入库的 `rewritten_title`。

**规则：写第 N 天之前，先按本批已入库的 rewritten_title 过一遍同事件关键词。**
```sql
SELECT substr(key,1,12), rewritten_title FROM news
WHERE substr(updated_at,1,10) >= '<本批起始日>' AND COALESCE(rewritten_title,'')!='';
```
发现重复对之后不要自己处理，**把两条都摆给用户**（只发1条 / 错开发 / 合成1条），让用户定。

## 4. gzh 稿会被 precheck 的 xhs 密度门报 FAIL —— 属预期

`gzh_draft_*.md` 如果对应素材是 `fmt=story lf=1`，`batch_precheck.py` 会用 xhs 口径判密度（ja×30%），必然报 FAIL。**这是通道差异，不是缺陷**：gzh 走「去魅测试 → 背景锚定 → 三维度评分」，合格线 7 分，不要为了过 xhs 密度门去硬扩正文。

## 5. 顿号行：批量一次机械修完，不要逐篇改

`行内 「、」≥2` 在 renwei 里就是「排比三连」的真实前置条件。批量时**一次脚本跑完所有 draft**（行内第 2 个及以后的「、」→ 中文间隔号 `·`），比逐篇改快一个数量级：

```python
for p in glob.glob('*.md'):
    L = open(p).read().split('\n')
    out = []
    for l in lines:
        if l.count('、') >= 2:
            idx = [i for i, c in enumerate(l) if c == '、']
            for j in idx[1:]:
                l = l[:j] + '·' + l[j+1:]
        out.append(l)
    open(p, 'w').write('\n'.join(out))
```
改完必须重跑 precheck（正文变短会影响字数门）。

## 7. 字数校准（本轮反复吃亏）

中文正文手写长度**普遍比预估短 ~40%**：估 900 字实际落 450–600，导致每批都要多花 2–3 轮补字。

- **动笔就按「目标字数 × 1.8」写**，或按「ja_len × 0.31 × 1.5」
- 每篇写完立刻跑 precheck 单篇，不要攒到批末统一爆发（skill 里 8/15 已经写过，本轮再次验证）
- 补字时加**整段**（+150~250 字），加一句话（+10~30 字）往往填不满门禁，会来回好几轮
