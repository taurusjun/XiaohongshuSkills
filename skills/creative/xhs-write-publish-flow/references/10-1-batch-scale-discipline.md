# 批量写稿的量级纪律与工具调用模式（10/1 实作）

## 1. 跨日积压的量级判断——先算规模，再决定怎么吞

10/1 开批时按跨日规则检查，发现 **9/28、9/29、9/30、10/1 四天全部未写**
（四日 `preselected=0` / `rewritten_title` 全空 / `score_dims` 全空）。
逐日 target 数：32 + 32 + 31 + 30 ≈ **125 篇**。

历史参照：`9-24-9-26-crossday-3day-batch-flow.md` 的 41 篇/3 天是此前的最大单次批次。
**125 篇约等于历史最大批次的 3 倍，单会话做不完。**

**规则：**
- 开批前先按 `S级 + A级 + AKB大TOP` 逐日累加，算出**总 target 数**，写进 todo 第一行。
- **总 target > 60 或未写日 ≥ 3 天 → 单日闭环，逐日推进，绝不并行、绝不交错。**
  即：day N 的 写稿 → precheck → renwei → 入库 → review → score_dims 全部落盘之后，
  才开 day N+1。
- **理由（硬约束，不是偏好）：** draft 只存在 /tmp/，DB 是唯一持久层。若先写完 4 天
  draft 再统一入库，中途碰到工具调用上限 → 后几天的稿子全部滞留 /tmp，DB 里没有任何
  痕迹，次日无法续跑（`8/17 实测截断` 与 `7/31 实锤` 是同一机制的两次发作）。
  单日闭环下，被截断时损失上限是「当天没写完的部分」，已落盘的日子不受影响。
- 顺序取**最新一天优先**（10/1 → 9/30 → 9/29 → 9/28），与既有跨日批实作一致。
- 单日闭环也做不完时，**如实报告已落盘的天数与剩余天数**，不要用「差不多写完了」
  掩盖。用户在 review 存档里能自己数出来。

## 2. 阶段A的工具调用模式（把 125 篇压进可执行预算）

### 2.1 读素材：`scripts/dump_ja.py`，不要 read_file 裸读

`read_file` 对超长行**静默截断**（~2000 字/行）。content_ja 直接落盘再 read_file，
5000 字素材只能拿到 2400 字，中后段引语全丢且不报错。
→ 一律 `python3 scripts/dump_ja.py <date> <前缀...>`（内部 textwrap 折行 500 字）。
→ 一次 dump 2~3 篇（输出约 8~15K 字），读完立刻写稿，不要一次拖 10 篇进上下文。

### 2.2 写 draft：一条 terminal 调用写 4~8 篇

用 `python3 - <<'PYEOF'` heredoc + dict，一次写入多篇
`/tmp/drafts<MMDD>/xhs_draft_<key12>.md`（首行 `## 标题`）。
逐篇 write_file 会把工具预算烧在调用开销上。

**文件名陷阱（10/1 实测踩到）：** 文件名里的 key 必须是**完整 12 位前缀**
（`xhs_draft_f7cb19970261.md`），写短了（`f7cb19`）→ precheck 归到 plan 里不存在的
key → 静默 `SKIP`，看起来像通过，实际这篇从未被检查过。

### 2.3 批量改稿脚本必须「不中断」

批量 patch 脚本里 `assert a in t` 或 `open()` 抛错 → **整个 heredoc 中止，
其后的所有 patch 静默丢失**。10/1 实测：`rw('f7cb19', ...)` 抛
FileNotFoundError，导致同脚本后面的 345622d0 修补全部没执行，直到下一轮 precheck
才发现。

**正确写法：**
```python
def rw(k, pairs):
    p = f'xhs_draft_{k}.md'
    try:
        t = open(p).read()
    except FileNotFoundError:
        print('NOFILE', k); return
    for a, b in pairs:
        if a not in t:
            print('MISS', k, a[:30]); continue   # 不 assert，不中断
        t = t.replace(a, b, 1)
    open(p, 'w').write(t)
```
改完必须**逐文件复核**（打印每个 key 的 MISS 行），不能假定都改上了。

### 2.4 precheck 的读法：

`batch_precheck.py` 对 plan.json 里没有的 key 输出 `SKIP`，**不计入 FAIL**。
每次必须核对三件事：① 末尾 `N 篇检查完毕` 的 N == 本轮 draft 数；
② 没有 `SKIP` 行；③ FAIL 数符合预期。

## 3. 正文长度：靠「写后实测」而不是预估

10/1 批 13 篇 story 里有 7 篇首轮不足（最低 452 字），又花了 12 轮扩充。

**根因：中文成稿字数**比落笔时的直觉估计**低 25~30%**。写「看起来 900 字」的段落，
实测往往 650~700。

**规则：**
- 动笔前按 `目标正文 = max(800, ja_len × 0.31)` 定字数（news 取 `ja_len × 0.31`，
  实践中 ~250~420 字起步）。
- **每写完 2~3 篇就立刻跑一次 precheck**，不要等整批写完再统一查——那时每篇都要
  重读才知道差多少。
- 扩充时优先用**素材里已中文化但还没写进去的细节**（引语、配角名、场景），而不是
  加形容词；补完必须重跑 假名 + renwei（扩充会重新引入假名和 renwei 命中）。

## 4. 顿号（、）是 news 稿的第一大 FAIL 来源

10/1 批 news 的 FAIL 全部来自顿号行，命中位置清一色是**并列人名/曲名/作品名**：
- 「一之濑瑠菜、Task have Fun的里仲菜月、山田爱、岸明日香、池本诗织」
- 「川荣李奈、木崎尤莉亚、入山杏奈、小林茉里奈」
- 「织田裕二、白洲迅、增田贵久、野吕佳代、桃色幸运草Z的玉井诗织、樱坂46的藤吉夏铃」
- 三首小分队曲的演唱者名单

**写稿时就拆掉，不要留给 precheck：**
1. 拆成两句（「她跟川荣李奈、木崎尤莉亚坐在同一桌。同桌还有入山杏奈和小林茉里奈。」）
2. 用「和 / 以及 / 等人」压缩（「还有一之濑瑠菜和 Task have Fun 的里仲菜月等人」）
3. 一句里最多留 1 个顿号。
注意**同一行里第二处顿号也计数**——比如人物名列表后面又写「露出双肩、胸口开得很低的
礼服」，两处加起来就触发 FAIL。改完一处处扫整行。

## 5. 两个高频 renwei 假阳性（10/1 批共修 6 处）

### 5.1 「的 + 路」格言公式

正则 `[^。，！？]{2,20}(的|之)(路|语言|镜子|货币|篇章|缩影|写照)` 会命中大量
**中文常用表达**，包括 `##` 小标题：

| 命中 | 改法 |
|------|------|
| `## 同龄的另一个人，走了相反的路` | `## 同龄的另一个人，选了另一种活法` |
| `整首走的是克制又冷的路子` | `整首唱得很克制，也很冷` |
| `走的不是摆姿势的路子` | `没有摆姿势的痕迹` |
| `但他在演员这条路上评价不低` | `但他在演戏这方面评价不低` |
| `## 四个已婚者，和两条走掉的路` | `## 四个已婚者，和两个退团的人` |

**`##` 小标题也要查**——10/1 有两处命中落在小标题行，正文改干净了标题还在。

### 5.2 「不是X而是Y」

会命中「既不是…也不是…」这类**自然否定句**：
- `但既不是回复也不是艾特` → `但既没有回复也没有艾特他`

10/1 其余 4 处 `exit 2`（单处非聚集）按 skill 约定直接接受，未强改。

## 6. 短句轰炸：`##` 标题下面的独行短句

把一句话单独成行放在 `##` 小标题下面（作为导语）→ 触发 `短句轰炸(连续短句)`。
10/1 实测 `2d7c82cdac02`：`## 雨里递过来的一把伞` / `预告片的第一句台词就定了调子。` /
（空行）/ 正文段。修法：把小标题下面那句**并进下面的正文段**，不做独立导语行。

## 7. 跨日同一事件的 merged 标记

同一事件跨两天入库时，**只在素材更全/更晚的那天成篇**，另一天全部挂 merged：
`preselected=1 + publish_xhs=0 + score_dims='merged-into-<主条key12>'`。

10/1 批实际用到：
- 新井彩永留学（9/30 `c83e00d9` ← 10/1 `9a332fdc` 成篇）
- 有吉×深泽 X 骚动（9/30 `fa573352` / `4eb2c88d` ← 10/1 `7cd2db60` 成篇）
- 和田まあや婚礼（9/30 `e8bfad0c` / 10/1 `7cdc44e2`、`322aab80` ← 10/1 `51a6cdca` 成篇）
- 増本绮良卒業 BACKS LIVE（9/30 `2e7371e6` ← 10/1 `95ff1f64` 成篇）

**主条被吸收的副条**保持 `preselected=0`（如 10/1 `6352a4b7` 作为 `0f68079b` 的
related，属预期状态），不要误判为漏写。

## 8. score_dims 落盘一次跑完，别逐条 UPDATE

story / news / merged 三类值可以合成一张 `[(value, key), ...]` 列表，
循环 `UPDATE news SET score_dims=? WHERE key=?` 后 `commit()` 一次。
验证查询必须用 `substr(key,1,12) IN (...)`——`WHERE key IN ('12位前缀')` 恒返回 0 行，
看着像「全部落盘失败」，实际是查询写错。
